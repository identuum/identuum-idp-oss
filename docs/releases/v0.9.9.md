# identuum-idp-oss v0.9.9 — release notes

Tag `v0.9.9` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.9`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.9`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`f13dee8`, which is tagged identuum-ui `v0.9.9`.

## Changes

The details are in `CHANGELOG.md` (`## v0.9.9`); what matters to an
operator and to an API caller:

- **Breaking: an API resource no longer takes a token lifetime.**
  `POST /api/v1/api-resources` and `PUT /api/v1/api-resources/:id` refuse a
  request body that contains `token_ttl_secs` — in any letter case, and with
  a `null` value too — with `400`
  `{"error":"unsupported_field","field":"token_ttl_secs",...}`. There is no
  deprecation window. **What you must change:** stop sending
  `token_ttl_secs`; the same request without it is served as before. No
  API resource response carries the field any more. Go callers of the
  exported `types` package lose the `TokenTTLSecs` fields of
  `APIResourceResponse`, `CreateAPIResourceRequest` and
  `UpdateAPIResourceRequest`.
- **Token lifetimes do not change.** The field never had an effect: an
  ordinary access token — a user's, and a `client_credentials` token for an
  API resource — lives one hour, as before. The agent-communication token
  keeps its own lifetime (5 minutes by default, at most 15 through
  `IDENTUUM_IDP_AGENT_COMMUNICATION_TOKEN_TTL`, never past its
  authorization). The stored column stays as legacy data: it is never read
  for issuance and never shown, and no migration changes or drops it.
- **The console** no longer offers, shows or sends an API resource's token
  lifetime: the create and edit forms, the list badge and the detail row are
  gone.
- **Create and update read the body strictly.** A body with data after its
  JSON object (a second document, trailing text) is refused with `400`
  `{"error":"invalid request"}`, where the first object used to be taken.

For contributors only (nothing in the binary changes): `make test-full` runs
beside a dev stack on its own ports, `make devseed-live` proves `make
dev-seed` with every printed credential and runs before the mint's e2e half,
and the gate judges move to lictor v0.4.6 and grype v0.120.1. See the
CHANGELOG.

## Upgrading from v0.9.8

No migration runs: the schema stays at `0051`. No route was added, removed
or renamed; the endpoint count is 159. The database, the data volume, the
URL, browser sessions, issued tokens and the signing keys carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.8.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.8-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.9/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for clients:** a create or update of an API resource
   that sends `token_ttl_secs` is refused (above), and one whose body carries
   anything after its JSON object is refused. Nothing else answers
   differently.

## Upgrading from v0.9.7 or earlier

Follow the `v0.9.8` notes first (and the earlier notes before them).

## Rolling back to v0.9.8

v0.9.9 adds no migration, so v0.9.8 starts on its database as it was.
Restore the compose file and recreate the containers:

```bash
cp docker-compose.v0.9.8.yml docker-compose.yml
docker compose up -d
```

After a rollback, a create or update with `token_ttl_secs` is accepted again
(and still has no effect on a token's lifetime).

## Known limitations

As in `v0.9.8`: a public client gets no refresh token; step-up and the other
second-factor proofs take only an authenticator code; an enrolment started in
Account settings lives in the running process for its five minutes; a token
minted for an API resource without an organization is active only to the
client it was issued to; resetting a user's password without email is an API
call; `IDENTUUM_IDP_TEST_ALLOW_PRIVATE_UPSTREAM_ISSUER` is for tests only;
requiring a verified email needs SMTP, a claim link needs
`IDENTUUM_IDP_UI_PUBLIC_BASE_URL`, the console and the OpenID Connect sign-in
keep separate sessions (D-023), and OSS runs one serving instance.

## Verification

`make verify-parallel`, the e2e mint, CI, the OpenID conformance run (both
plans against the committed floor), the upgrade from `v0.9.8` with data and
the rollback (a site_admin's and an org_admin's sign-in with their second
factor, a refresh token and the signing keys, both ways), the published
image digest, the binaries and a smoke test of the published compose file
are recorded with the publication.

SemVer: `0.9.9` is a patch release by the `v0.9.5` precedent, where an
owner ruling removed a claim in a patch. Here an owner ruling (P-081..P-084)
removes a field that never had an effect: create and update refuse it, and
no response carries it. No migration; no route was added, removed or
renamed.
