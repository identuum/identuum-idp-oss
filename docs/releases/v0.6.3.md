# identuum-idp-oss v0.6.3 — release notes

Tag `v0.6.3` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.6.3`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The binary embeds identuum-ui
`1298670` (tree digest
`0cbbd2a6c0b53d15aa4ffcb1deea621ebb4466a012963d13c1f673deb42df851`), the
tree identuum-ui `v0.3.3` publishes.

## Theme: a deleted client is gone at once, and a refused change changes nothing

A patch release of security and correctness fixes. Nothing a `v0.6.2`
install relies on changes shape: same URL, same single container, same
database schema, same cookies. No route, field or response shape is
removed or renamed. Some requests that used to succeed are now refused;
those are the security fixes, listed under Upgrading.

- **A deleted client's tokens stop at once.** Userinfo and introspection
  judged an access token by its signature, subject and revocation, never
  its client, so a deleted client's unexpired token kept working until it
  expired.
  - Userinfo answers `401 invalid_token` and introspection
    `{"active":false}` for a token whose client no longer exists. A failed
    client lookup answers 503 rather than trusting the token.
  - `DELETE /api/v1/clients/:id` revokes the client's refresh tokens, and
    the access tokens issued with them, before it deletes the client.
    Authorization codes already issued to it cannot be exchanged: the token
    endpoint authenticates the client first.
- **Client delete tells the truth.** Deleting another organization's
  client or an unknown id answered `200 {"deleted": id}` and recorded a
  `client.deleted` audit event while deleting nothing. It now answers 404
  and records nothing.
- **A refused role change or disable changes nothing.** In `v0.6.2` a role
  change or disable whose session revocation failed answered 503 but kept
  the change. The revocation now runs first; if it fails, nothing is
  saved.
- **The embedded UI is identuum-ui `v0.3.3`.** A signed-in user opening `/`
  lands on their role's home (`/site-admin`, `/org-admin` or
  `/dashboard`) instead of the sign-in page. `/reset-link` says it is not
  available on this installation, as OSS offers no admin reset link.

The full list is in `CHANGELOG.md`, `## v0.6.3`.

## Upgrading from v0.6.2

The database, the data volume, the URL and the browser sessions carry over.
No migration runs.

1. **Back up.** Keep a copy of the current compose file and dump the
   database:

   ```bash
   cp docker-compose.yml docker-compose.v0.6.2.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.6.2-backup.sql
   ```

2. **Replace the compose file with the `v0.6.3` one and recreate the
   container.** Only the `identuum-idp` image line and comments change;
   carry over any edits you made to the old file.

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.6.3/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **Migrations.** None: `v0.6.3` uses the schema `v0.6.2` uses
   (`0001`–`0040`).

4. **Sessions.** Nobody signs in again: sessions live in the database and
   the cookies are unchanged. Accounts, organizations, clients, roles and
   enrolled authenticators are unchanged. Tokens held by clients that were
   deleted before the upgrade stop working at once, even if they have not
   expired yet.

5. **New answers a client may see.** Each is a refusal of something the
   rules never allowed, or a status that now says what happened:
   - `DELETE /api/v1/clients/:id`: `404 {"error":"not found"}` for another
     organization's client or an unknown id, where it answered
     `200 {"deleted": id}`.
   - `DELETE /api/v1/clients/:id`: `503 {"error":"revocation_failed"}`
     when the client's tokens could not be revoked. The client is not
     deleted; retry.
   - `GET /api/v1/oidc/userinfo`: `401` with `WWW-Authenticate` error
     `invalid_token` for an access token whose client was deleted.
     `POST /api/v1/oauth/introspection` answers `{"active":false}` for it.
     Either answers 503 if the client could not be looked up.
   - `PUT /api/v1/users/:id`: a `503 {"error":"revocation_failed"}` role
     change or disable is no longer saved; retry it.

## Rolling back to v0.6.2

`v0.6.3` adds no migration, so a `v0.6.2` binary reads the same database.

```bash
cp docker-compose.v0.6.2.yml docker-compose.yml
docker compose up -d
```

Sessions carry over in both directions. Data written under `v0.6.3` stays.
`v0.6.2` again accepts a deleted client's unexpired tokens, answers 200 to
a client delete that deletes nothing, and keeps a role change whose
revocation failed. If the database itself must go back, restore the step-1
dump into a stopped install; that loses everything written after the dump.

## Known limitations

- **The published image does not record its commit.** `publish-image.yml`
  passes `VERSION` but no `COMMIT` build argument, so the image's build
  commit is the Dockerfile default `unknown`. The tag, the `sha-<commit>`
  image tag the workflow also pushes, and the provenance attestation still
  name the commit.
- **OSS sends no initial verification mail.** Nothing in the binary sends
  a new account its first verification link; a user gets one by asking
  `POST /api/v1/auth/resend-verification`, when SMTP is configured.
