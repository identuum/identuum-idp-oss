# identuum-idp-oss v0.9.6 — release notes

Tag `v0.9.6` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.6`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.6`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`57482c5`.

## Changes

This release fixes what a functionality review of `v0.9.5` found broken in
sign-in and app registration. Each fix has a test that failed first. The
details are in `CHANGELOG.md` (`## v0.9.6`); what matters to an operator:

- **Public clients work.** A single-page or mobile app registered as a
  public client (no secret) completes the sign-in: it exchanges its code with
  `client_id` and the PKCE `code_verifier`. It receives no refresh token, so
  it signs in again through `/authorize` when the access token expires.
- **Recovery codes sign in.** Where the sign-in asks for the authenticator
  code, one unused recovery code works instead, once. The console's code
  field takes it.
- **Sign-in tells you to wait instead of "invalid".** Repeated failures from
  one address, and too many wrong authenticator codes, now answer
  `429 login_throttled` with `Retry-After`, the right password or code
  included; the console says how long. Before, the right password was
  answered "invalid credentials" and the right code "invalid code". The
  limits are unchanged.
- **`reset-org-admin-mfa`** also clears the wrong codes counted against the
  removed factor, so the reset administrator's new code is not refused.
- **Upstream OIDC (sign-in through another provider)** works as
  `docs/guides/oidc-upstream-login.md` says: the guide shows the API's real
  request body, and the callback it tells you to register is used when you
  configure none, and the provider's `email_domains` are now kept when it is
  saved (they were dropped before, so no upstream user could sign in). A
  test setting lets you try it against a provider on your own network; see
  the guide.
- **The OpenID conformance harness** (`make openid-conformance`) runs again.

## Upgrading from v0.9.5

No migration runs, no route was removed or renamed, and the endpoint count
stays 157. The database, the data volume, the URL, browser sessions and
issued tokens carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.5.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.5-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.6/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for clients:**
   - **Sign-in clients** that read `401 invalid_credentials` as "wrong
     password" now also see `429 login_throttled` while a per-address limit
     holds; wait `Retry-After` seconds. The same `429` answers the code step
     (`POST /api/v1/auth/login/mfa`) while a user's wrong-code budget is
     spent.
   - **Discovery** lists `none` among the token endpoint's auth methods.

4. **An upstream OIDC provider configured before v0.9.6** lost its
   `email_domains` when it was saved, so it signed nobody in. Send its
   configuration again (`PUT /api/v1/organizations/{org_id}/identity-provider`,
   the same body as the create in `docs/guides/oidc-upstream-login.md`; an
   omitted `client_secret` keeps the stored one).

## Upgrading from v0.9.4 or earlier

Follow the `v0.9.5` notes first (three migrations, `0048` to `0050`).

## Rolling back to v0.9.5

v0.9.6 adds no migration, so v0.9.5 runs on the same database. Restore the
compose file and recreate the containers:

```bash
cp docker-compose.v0.9.5.yml docker-compose.yml
docker compose up -d
```

After a rollback, a public client cannot redeem its code again, a recovery
code no longer signs in through the sign-in page, and the waits answer
`401` as before. Data written under v0.9.6 stays readable by v0.9.5.

## Known limitations

- **A public client gets no refresh token.** The refresh grant needs client
  authentication.
- **Step-up and the other second-factor proofs** (MFA disable, recovery-code
  regeneration, skip consent) still answer a spent wrong-code budget as a
  wrong code, and take only an authenticator code.
- **`IDENTUUM_IDP_TEST_ALLOW_PRIVATE_UPSTREAM_ISSUER`** turns the SSRF guard
  off for upstream sign-in; it is for tests only.
- **The console has no page to configure an upstream provider**; it is set
  through `POST /api/v1/organizations/{org_id}/identity-provider`.
- **Other findings of the same review remain open** (among them: TOTP
  enrolment from the account settings, scope templates in the console, the
  IdP exiting when the database is down at boot, undocumented signing-key
  rotation). They are tracked for later releases.
- **Requiring a verified email needs SMTP**, **a claim link needs
  `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**, **the console and the OpenID Connect
  sign-in keep separate sessions** (D-023), and **OSS runs one serving
  instance** — as in `v0.9.5`.
