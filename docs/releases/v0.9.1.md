# identuum-idp-oss v0.9.1 — release notes

Tag `v0.9.1` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.1`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.9.1`, `dry_run: false`). The
binary embeds identuum-ui `1f743e9` (tree digest
`8c2232e0a1f190d5f90b1242920fce119245d07a0c1dd62ee97c4aedade02bf6`), the
tree identuum-ui `v0.6.1` publishes.

## Fixes

- **Expected sign-in answers are no longer failed requests.** With
  `X-Identuum-Login-Step-Status: 200`, a pending self-registrant's correct
  password (`403 registration_pending` at `POST /api/v1/auth/login`) and an
  organization-lookup miss (`404 organization_not_found` at
  `GET /api/v1/auth/organization-lookup`) answer 200 with the same body — no
  session, cookie or token. Without the header every answer is unchanged.
  The embedded console sends it on both calls, so the browser logs neither,
  and the pending refusal reads "Your account is waiting for an
  administrator's approval." (it read "Login failed. Try again.").
- **The image publish proves the image serves before pushing it.**
  `publish-image.yml` starts the loaded amd64 image against a throwaway
  Postgres (its own entrypoint: migrate, then serve) and requires `/readyz`
  200, the newest migration applied and `version` naming the tag and
  commit, before the scan and the push. `v0.9.1` is its first run.
- **The embedded UI** is identuum-ui `v0.6.1`. Its changes for
  identuum-idp-ce follow capabilities this binary does not send; on
  identuum-idp-oss the console behaves as in `v0.9.0`.

The full list is in `CHANGELOG.md` (`## v0.9.1`).

## Upgrading from v0.9.0

No migration; `go.mod` and `go.sum` unchanged; no route, field or response
shape removed or renamed (the canonical endpoint count stays 157). The
database, the data volume, the URL, the browser sessions and issued tokens
carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.0.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.0-backup.sql
   ```

2. **Replace the compose file and recreate the container:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.1/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **What changes for clients:** only a client that sends
   `X-Identuum-Login-Step-Status: 200` sees a difference — the two answers
   above arrive as 200 with the same body.

## Rolling back to v0.9.0

The schema is the same, so restore the previous compose file and recreate
the container:

```bash
cp docker-compose.v0.9.0.yml docker-compose.yml
docker compose up -d
```

Sessions and tokens carry over. Restore the step-1 dump only if the
database itself must go back; that loses everything written after it.

## Known limitations

- **Requiring a verified email needs SMTP**; without it the setting is
  refused (`400 smtp_not_configured`) and the console disables it.
- **A claim link needs `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**; without it
  nothing is issued (`409 claim_url_unavailable`).
- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions.
- **Compose over IPv6** is documented, not yet proven on a Linux Docker
  host.
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is
  a Professional+ capability.
