# identuum-idp-oss v0.6.2 — release notes

Tag `v0.6.2` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.6.2`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The binary embeds identuum-ui
`d5b5602` (tree digest
`220b0001e69c15dbd43cee96147b39d999ff7619acb6031eeef43418238f000b`), the
tree identuum-ui `v0.3.2` publishes.

## Theme: an organization cannot lock itself out, and a role change is immediate

A patch release of security and correctness fixes. Nothing a `v0.6.1`
install relies on changes shape: same URL, same single container, same
database schema, same cookies. No route, field or response shape is
removed or renamed. Some requests that used to succeed are now refused;
those are the security fixes, listed under Upgrading.

- **org_admin safety rules** (the same rules as identuum-idp-ce,
  contracts/AdminPermissionsModel.md line 3). Through the admin routes an
  org_admin:
  - can no longer disable, demote or delete itself;
  - can no longer change its own roles or reset its own MFA;
  - can no longer disable, demote or delete its organization's last active
    org_admin. The check and the write run in one transaction with the
    organization row locked, so two admins disabling each other at once
    leave one.

  The site_admin's recovery of an organization that lost its admins is
  unchanged.
- **A role change takes effect at once.** A bearer's role came from its
  access token, so a demoted org_admin kept its rights until the token
  expired (up to one hour). A role change or a disable through
  `PUT /api/v1/users/:id` now revokes the user's sessions and refresh
  tokens: every session-bound access token and cookie dies on its next
  request. A revocation that fails is reported, not swallowed.
- **Honest statuses on user PUT and DELETE.** `DELETE /api/v1/users/:id`
  answered 404 for any failure, including a database fault. Unidentified
  actors got 500 (PUT) or 404 (DELETE).
- **The mail pages follow SMTP.** `GET /api/v1/component` reports
  `mail_ceremonies`, true only when `IDENTUUM_IDP_SMTP_HOST` and a sender
  are set. Without them the embedded UI (identuum-ui `v0.3.2`):
  - hides "Forgot password?";
  - says the reset, verification and activation pages are not available,
    instead of offering forms whose mail could not arrive.

  The forgot-password page reports "sent" only when the IdP answered 2xx.
- **Two more capabilities** in `GET /api/v1/component`:
  `admin_reset_link: false` (an identuum-idp-ce surface) and
  `user_approval: true`.
- **Install from GitHub Releases.** The install line downloads the compose
  file from `releases/latest/download/docker-compose.yml`; every release
  carries its pinned compose file and its `.sha256` as assets.

The full list is in `CHANGELOG.md`, `## v0.6.2`.

## Upgrading from v0.6.1

The database, the data volume, the URL and the browser sessions carry over.
No migration runs.

1. **Back up.** Keep a copy of the current compose file and dump the
   database:

   ```bash
   cp docker-compose.yml docker-compose.v0.6.1.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.6.1-backup.sql
   ```

2. **Replace the compose file with the `v0.6.2` one and recreate the
   container.** Only the `identuum-idp` image line and comments change;
   carry over any edits you made to the old file.

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.6.2/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **Sessions.** Nobody signs in again: sessions live in the database and
   the cookies are unchanged. Accounts, organizations, clients, roles and
   enrolled authenticators are unchanged. From now on, changing a user's
   role or disabling a user signs that user out everywhere.

4. **New answers a client may see.** Each is a refusal of something the
   rules never allowed, or a status that now says what happened:
   - `403 {"error":"cannot_change_self"}`: an org_admin changing its own
     active state or role (`PUT /api/v1/users/:id`) or deleting itself
     (`DELETE`). Its own name and profile stay editable.
   - `403 {"error":"cannot_change_own_roles"}`: an org_admin assigning or
     removing its own roles (`/api/v1/users/:id/roles`).
   - `403 {"error":"cannot_reset_self"}`: an org_admin resetting its own
     MFA through `POST /api/v1/users/:id/recovery/reset-mfa`. The user's
     own factor is managed in account settings.
   - `409 {"error":"last_org_admin"}`: disabling, demoting or deleting the
     organization's last active org_admin.
   - `503 {"error":"revocation_failed"}`: a role change or disable was
     saved, but the user's sessions could not be revoked. Retry.
   - `DELETE /api/v1/users/:id`: `500 {"error":"internal_error"}` for a
     server fault, where it answered 404. PUT and DELETE answer
     `401 {"error":"unauthorized"}` for an unidentified actor.

5. **Mail.** If your users rely on the reset, verification or activation
   mails, make sure `IDENTUUM_IDP_SMTP_HOST` and `IDENTUUM_IDP_SMTP_FROM`
   (or `_USERNAME`) are set. Without them those pages now say they are not
   available, and the sign-in form asks the user to contact an
   administrator.

## Rolling back to v0.6.1

`v0.6.2` adds no migration, so a `v0.6.1` binary reads the same database.

```bash
cp docker-compose.v0.6.1.yml docker-compose.yml
docker compose up -d
```

Sessions carry over in both directions. Data written under `v0.6.2` stays.
`v0.6.1` again allows the self and last-admin changes above, keeps a
demoted user's tokens until they expire, and shows the mail pages whether
or not SMTP is set. If the database itself must go back, restore the
step-1 dump into a stopped install; that loses everything written after
the dump.

## Known limitations

- **The published image does not record its commit.** `publish-image.yml`
  passes `VERSION` but no `COMMIT` build argument, so the image's build
  commit is the Dockerfile default `unknown`. The tag, the `sha-<commit>`
  image tag the workflow also pushes, and the provenance attestation still
  name the commit.
- **OSS sends no initial verification mail.** Nothing in the binary sends
  a new account its first verification link; a user gets one by asking
  `POST /api/v1/auth/resend-verification`, when SMTP is configured.
- **A failed revocation keeps the change.** A `503 revocation_failed` role
  change or disable is saved. Resending the same value may not revoke
  again: the role no longer changes, and the user is already disabled.
  Until that is decided (rollback or idempotent re-revoke), retry by
  signing the user out from the sessions page, or restart the change.
