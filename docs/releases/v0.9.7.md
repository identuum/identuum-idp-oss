# identuum-idp-oss v0.9.7 — release notes

Tag `v0.9.7` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.7`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.7`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`75353da`.

## Changes

This release closes the remaining findings of the functionality review of
`v0.9.5` and the two items `v0.9.6` left open. Each code fix has a test that
failed first. The details are in `CHANGELOG.md` (`## v0.9.7`); what matters
to an operator:

- **Users can add an authenticator from Account settings.** The button
  answered "not found" on OSS. It now asks for the current password, shows
  the QR code, takes the first code and shows ten recovery codes once.
- **The proof routes say "wait".** After too many wrong codes, step-up, MFA
  disable, recovery-code regeneration and skip consent answer
  `429 login_throttled` with `Retry-After`, like sign-in.
- **The IdP waits for its database.** If PostgreSQL does not answer at
  start, the IdP stays up and reports NOT-SERVING (`/health` names the
  `database` fault) and starts serving when the database answers. It used
  to exit, and the compose install restarted in a loop.
- **A resource server with a URL audience can use HTTP Basic** at
  introspection (the credentials are form-decoded, RFC 6749 §2.3.1).
- **"Last login" is recorded** for every completed sign-in.
- **The setup wizard says why it refuses a password**, and its hint states
  the whole rule.
- **Console:** held sign-ups show "Awaiting approval"; scope templates show;
  the service-account form matches the IdP; an active organization's
  administrator who never accepted the invite can be re-invited; the audit
  log reaches older events; a new **Sign-in provider** page (Settings →
  Configure the sign-in provider) sets up the organization's upstream OpenID
  Connect provider, as `docs/guides/oidc-upstream-login.md` describes.
- **Docs:** losing the at-rest key and how to recover; signing-key rotation;
  resetting a user's password without email; the service-account bundle API.

## identuum-ui numbering

From this release identuum-ui uses the same version numbers as
identuum-idp-oss (owner ruling, 2026-10-05). The console embedded here is
identuum-ui `v0.9.7` (`package.json` `0.9.7`). The earlier identuum-ui tag
`v0.9.6` (on `57482c5`, `package.json` `0.6.2`) stays as it is.

## Upgrading from v0.9.6

No migration runs and no route was removed or renamed. Two routes are added
(`POST /api/v1/mfa/setup/initiate` and `/complete`); the endpoint count is
159. The database, the data volume, the URL, browser sessions and issued
tokens carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.6.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.6-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.7/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for clients:**
   - **MFA disable, recovery-code regeneration and skip consent** answer
     `429 login_throttled` with `Retry-After` (they answered `401
     invalid_code`) while a user's wrong-code budget is spent.
   - **`POST /api/setup/complete`** answers `400 weak_password` with a
     `message` for a refused password (it answered `400
     setup_complete_failed`).
   - **A process supervisor** that restarted the IdP when it exited with
     the database down now sees it stay up and NOT-SERVING instead.

## Upgrading from v0.9.5 or earlier

Follow the `v0.9.6` notes first (and the `v0.9.5` notes before them for
v0.9.4 or earlier).

## Rolling back to v0.9.6

v0.9.7 adds no migration, so v0.9.6 runs on the same database. Restore the
compose file and recreate the containers:

```bash
cp docker-compose.v0.9.6.yml docker-compose.yml
docker compose up -d
```

After a rollback, Account settings cannot add an authenticator again (the
routes are gone; authenticators already added keep working), the proof
routes answer a spent budget with `401`, and a database that is down at boot
ends the process. Data written under v0.9.7, including `last_login_at`,
stays readable by v0.9.6.

## Known limitations

- **A public client gets no refresh token.** The refresh grant needs client
  authentication.
- **Step-up and the other second-factor proofs** take only an authenticator
  code, not a recovery code.
- **An enrolment started in Account settings** lives in the running process
  for its five minutes; after a restart the user starts it again.
- **The organization's `service_account_expiry_days`** is not applied to a
  new service account; one without an expiry date never expires.
- **Resetting a user's password without email** is an API call
  (`PUT /api/v1/users/{id}`); the console has no button for it.
- **`IDENTUUM_IDP_TEST_ALLOW_PRIVATE_UPSTREAM_ISSUER`** turns the SSRF guard
  off for upstream sign-in; it is for tests only.
- **Requiring a verified email needs SMTP**, **a claim link needs
  `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**, **the console and the OpenID Connect
  sign-in keep separate sessions** (D-023), and **OSS runs one serving
  instance** — as in `v0.9.6`.

## Verification

`make verify-parallel`, the e2e mint, CI, the OpenID conformance run (both
plans against the committed floor), the upgrade from `v0.9.6` with data and
the rollback, the published image digest, the binaries and a smoke test of
the published compose file are recorded with the publication.

SemVer: `0.9.7` is a patch release. No migration; no route was removed or
renamed; two routes were added. Three answers change: a spent wrong-code
budget on the proof routes answers `429` instead of `401`, a refused setup
password answers `weak_password` instead of `setup_complete_failed`, and a
database that is down at boot is waited for instead of ending the process.
