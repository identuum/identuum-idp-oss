# identuum-idp-oss v0.9.13 — release notes

Your connected apps, administrator reset links, a sign-in policy per
organization, mail with a display name, and plain answers where the server
refuses. The release embeds identuum-ui `6643cd0`
(`6643cd0f4018e4232ce852162e875404d4bf3ce4`, export tree digest
`ac562b0a18f8364a197b77b3e7dd27a0ab33cd498f47aabac36968bbda71ef63`). The identuum-ui `v0.9.13` tag is created on that
revision at publication.

This page traces the changes in `v0.9.12..c138ed1`: 42 commits
(`git rev-list --count v0.9.12..c138ed1`, measured before the notes
commit). The release tag commit, its Linux image index digest and its
binary hashes are published with the release. Image publication uses
`publish-image.yml` on the release tag with `latest_tag: false`. Binary
publication uses `publish-binaries.yml` on the same tag.

## What changes for you

- **If you send mail with a display name** (`IDENTUUM_IDP_SMTP_FROM` set to
  `Name <address>`): mail now leaves. A sender that is not one email
  address is refused at startup with a plain line naming the variable; the
  server keeps serving and mails nothing.
- **If you are a member:** Account settings lists the applications that hold
  access to your account, and you can remove one.
- **If you are an administrator:** you can give a member a one-time reset
  link instead of setting a password. A password you set for someone else
  must now be changed at the next sign-in and expires after 24 hours,
  unless you send `"must_change_password": false`.
- **If your organization lets members sign in only through a provider
  (`idp_only`):** it can no longer be left without an active provider.
- **If two administrators edit the same application in the console:** the
  later save from an older page is refused with a plain message instead of
  undoing the newer save.
- **If you use email addresses in more than one organization:** read the
  first item under "Known limitations" before you upgrade.

## Changes

The full list, with the exact wording of every response, is the
`v0.9.13` section of [CHANGELOG.md](../../CHANGELOG.md). In short:

### Accounts and sign-in

- `GET` and `DELETE /api/v1/me/consents`: a member lists and removes the
  applications that hold access. Removing access ends that application's
  refresh tokens for the member.
- `POST /api/v1/users/{id}/recovery/reset-link`, with
  `GET /api/v1/auth/reset-link/validate` and `POST /api/v1/auth/reset-link`:
  an administrator's one-time reset link, shown once, valid 24 hours, never
  mailed. A redeem whose other sign-ins could not be ended answers
  `500 sessions_not_ended`.
- An administrator-set password (create or `PUT /api/v1/users/{id}`) asks
  for a change and expires 24 hours after it was set; an administrator
  setting its own password chooses it. The self-service reset sends
  nothing to a member who cannot use a local password.
- Upstream sign-in reads the email from userinfo when the ID token lacks
  it, refuses a pending invitee or a registrant waiting for approval, and
  sends a refused sign-in to `/login?reason=<code>`.

### Organizations, providers and applications

- `idp_only` needs an active provider, and its last provider cannot be
  deleted.
- A provider `PUT` that changes `active` or `priority` is refused with a
  plain message; nothing is saved.
- `PUT /api/v1/clients/{id}` takes `expect_updated_at`; a save from an
  outdated page answers `409 client_changed`.
- A client create that binds a service account holds the account while it
  saves and checks it again.
- `POST /api/v1/organizations` answers a duplicate domain `409
  domain_exists` and a duplicate name `409 slug_exists`.

### Mail and audit

- `IDENTUUM_IDP_SMTP_FROM` with a display name delivers; the envelope
  carries the bare address.
- `GET /api/v1/audit/event-types` lists the event types the server records;
  the console's audit filter uses it.

### Console (identuum-ui `6643cd0`)

- Account settings "Applications" tab; reset links and the 24-hour expiry
  on the user page; a sign-in policy control and plain provider texts in
  Settings; an application edit conflict banner; plain refusal words on the
  sign-in page; the audit filter reads the server's list; the console works
  on a phone (below 768 px the menu becomes a drawer).

### The four known issues of v0.9.12

- Mail with a display name in `IDENTUUM_IDP_SMTP_FROM` was not sent and no
  error was shown: **fixed.**
- The console's audit-log filter offered only some of the event types the
  server records: **fixed** (the server's list and the console).
- A re-sent invitation and the organization activation message do not name
  the organization: **still open**, planned for v0.9.14.
- The console's service-account card showed no result after an unlink or a
  second link: **fixed** (console).

The v0.9.12 limitation "for the six fields the console form sends, the save
that arrives last still wins" is **fixed**: the console sends
`expect_updated_at`, and an outdated save is refused.

## Upgrading from v0.9.12

This release adds one SQL migration, `0055_users_admin_password_set_at.sql`.
The tracked `migrations/` directory contains 55 SQL files, head `0055`
(`git ls-files 'migrations/[0-9][0-9][0-9][0-9]*.sql' | wc -l`).

- 0055 adds the nullable column `users.admin_password_set_at`. Rows written
  before the upgrade keep NULL, so no existing password expires and nobody
  is locked out by the upgrade.

Six routes are added; the endpoint count goes from 160 to 166
(`grep -c . tools/api-docgen/testdata/endpoints.manifest.txt`).

1. Back up the database, the Compose file and the matching encryption key,
   as `docs/OPERATOR-GUIDE.md` says.
2. If `IDENTUUM_IDP_SMTP_FROM` (or `IDENTUUM_IDP_SMTP_USERNAME` in its
   place) is not one email address, fix it first, or mail stays off.
3. Pull the digest-pinned v0.9.13 Compose file and start it. The migration
   runs at start.
4. Check `/readyz` and sign in.

## Rolling back to v0.9.12

The v0.9.12 server refuses the newer schema. Restore the verified
pre-upgrade backup into an empty database before you start v0.9.12; all
changes since the backup are lost. This is backup and restore, not an
in-place migration-down procedure. Reset links issued on v0.9.13 stop
working, and administrator-set passwords no longer expire.

## Known limitations

- **One email address in two organizations breaks email sign-in for both
  accounts.** When the same address belongs to a live account in two
  organizations, password sign-in and passkey sign-in by email fail for
  both accounts, because sign-in looks the address up across all
  organizations. v0.9.12 behaves the same. `POST /api/v1/organizations`
  does not refuse an initial administrator whose address has an account in
  another organization; `409 email_exists` is not enforced across
  organizations until v0.9.14. Until then, keep every address unique
  across organizations. The fix, planned for v0.9.14, allows one address
  per server. See [KNOWN_ISSUES.md](../../KNOWN_ISSUES.md).
- A passkey or provider sign-in does not ask for the password change an
  administrator requested, and does not apply the 24-hour expiry. Give such
  members a reset link instead of setting a password
  ([KNOWN_ISSUES.md](../../KNOWN_ISSUES.md)).
- A re-sent invitation or activation email does not name the organization
  (v0.9.14).
- CE customer-smoke licensed UI checks were not run for v0.9.13 (licence
  signing key unavailable); the CE stack build and reachability were proven
  by the owner's dry run on 2026-10-13.
