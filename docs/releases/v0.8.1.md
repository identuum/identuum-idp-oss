# identuum-idp-oss v0.8.1 — release notes

Tag `v0.8.1` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.8.1`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.8.1`, `dry_run: false`). The
binary embeds identuum-ui `4e4a637` (tree digest
`fa82552b109f5677ae5236113670996d3ed60e96be166cd1eae68172b6659639`), the
tree identuum-ui `v0.5.1` publishes.

## Theme: a patch for the console

- **Assign administrator invites the first administrator** (GitHub issue
  #1). An organization created without an admin email is active with no
  administrator; its page offered "Assign administrator", but that page
  could only re-issue a pending administrator's activation and answered
  "already active". It now asks for the administrator's email (and an
  optional name) and shows a one-time invitation to hand over; the link is
  also mailed when email delivery (SMTP) is configured. The rule it uses is
  unchanged: a site admin may invite an organization's first
  administrator, and only while it has none. A pending activation and the
  recovery state keep the re-issue.
- **The embedded UI's next moves to 16.3.6** (GHSA-vcvr-r3jv-pc5j, remote
  code execution in `next/og` `ImageResponse`). The console is a static
  export served by this binary: no Next server runs, and the UI does not use
  `next/og`, so the vulnerable path was never reachable here. The export's
  files are byte-identical to the previous build's (same tree digest).

## Upgrading from v0.8.0

None. No migration, no configuration, no route, field or response shape
changes. Replace the image (or the binary) and start it; sessions carry
over.

## Rolling back to v0.8.0

Run the `v0.8.0` image (or binary) against the same database; nothing to
undo:

```bash
cp docker-compose.v0.8.0.yml docker-compose.yml
docker compose up -d
```

An invitation issued from the new form stays valid under `v0.8.0` (the
route is the one `v0.8.0` already had); only the form disappears.

## Known limitations

- **Separate sessions.** The console and the OpenID Connect sign-in keep
  separate sessions: signing in to one does not sign in to the other, and
  `end_session` does not sign the console out.
- **Older audit rows** carry `organization_id` only where their metadata
  named the organization; the others keep their earlier visibility. The
  OSS log is plain and retention-pruned (30 days by default); it has no
  hash chain.
- **A console sign-in that fails** for a known email is recorded as
  `anonymous` (no password was proven).
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is
  a Professional+ capability.
