# identuum-idp-oss v0.9.0 — release notes

Tag `v0.9.0` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.0`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.9.0`, `dry_run: false`). The
binary embeds identuum-ui `36a3827` (tree digest
`4e2f073c04be1dbd43e31526b885220306b2f8d1e19331cea71c528a27f63db5`), the
tree identuum-ui `v0.6.0` publishes.

## Theme: hand an organization over, let people sign up

- **Organization claim links** (D-022). A site administrator issues a
  one-time claim link for an active organization with no administrator
  (`POST /api/v1/organizations/:id/claim`, or *Issue claim link* on the
  organization's page). An optional email binds the link and is mailed
  when SMTP is configured; issuing again retires the earlier link. Whoever
  redeems it at `/claim` sets a password, becomes the organization's
  administrator and enrols MFA at first sign-in. A redemption checks the
  organization at that moment: it must still be active and still have no
  active administrator.
- **Self-registration** (D-021), behind two switches that are both **off**:
  the instance switch (site administrator, *Settings → Self-registration*)
  and each organization's policy (its administrator, *Organization
  settings → Self-registration*: open, hold for approval, require a
  verified email, email domains). The public page is
  `/register/<org-slug>`; the API is
  `GET`/`POST /api/v1/auth/register/:org_slug`. A self-registrant is always
  an `org_user`. The sign-up answers a closed, unknown or `idp_only`
  organization, and a new or existing address, identically (202); only a
  password the open organization's policy refuses answers
  `400 weak_password`. Requiring a verified email needs SMTP. With approval
  on, the account waits (`403 registration_pending` at sign-in) until the
  organization administrator approves or rejects it on the Users page.
  Rate-limited per IP (an IPv6 client by its /64) and per organization;
  audited.
- **Archived organizations in the console** offer no action but Restore.
- **The embedded UI** is identuum-ui `v0.6.0` (next 16.3.8).

The full list is in `CHANGELOG.md` (`## v0.9.0`).

## Upgrading from v0.8.2

Measured against `v0.8.2`: migration `0043` (self-registration: a one-row
`instance_settings` table with the switch off, two organization columns
defaulting to off and empty, a nullable `users.registration_state`), all
additive; `go.mod` and `go.sum` unchanged. The image applies `0043` when it
starts; the bare binary needs
`identuum-idp migrate "$IDENTUUM_IDP_DATABASE_URL"` before it starts. The
database, the data volume, the URL, the browser sessions and issued tokens
carry over. **Self-registration stays off** until a site administrator turns
the instance switch on and an organization opens its own sign-up.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.8.2.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.8.2-backup.sql
   ```

2. **Replace the compose file and recreate the container:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.0/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **What changes for clients and operators:**
   - **New routes** (canonical endpoint count 148 → 157):
     `POST /api/v1/organizations/:id/claim`;
     `GET`/`PUT /api/v1/settings/self-registration`;
     `GET`/`PUT /api/v1/organizations/:id/registration`;
     `GET /api/v1/organizations/:id/registrations`;
     `POST /api/v1/users/:id/reject`;
     `GET`/`POST /api/v1/auth/register/:org_slug`.
   - **Approval:** `POST /api/v1/users/:id/approve` approves a
     self-registrant held for approval; it no longer clears an `org_user`'s
     `banned` flag (re-enable a disabled user with
     `PUT /api/v1/users/:id` `{"active": true}`, the console's *Enable*).
   - **Claim redemption** requires an active organization with no active
     administrator at the moment of redemption (it required an inactive
     organization, so no link a site administrator could issue was
     redeemable). A link whose organization no longer qualifies is retired.
   - Accounts that were not self-registered keep the sign-in rule they had.

## Rolling back to v0.8.2

`0043` is additive, and the `v0.8.2` binary does not know it. First make
sure no sign-up is waiting for approval — a pending self-registrant who has
verified their email would look like an ordinary verified user to
`v0.8.2` and could sign in unapproved. Approve or reject each one on the
Users page; the SQL below refuses to run while one is left. Then undo
`0043` and run the `v0.8.2` image:

```bash
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U identuum_idp identuum_idp <<'SQL'
BEGIN;
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM users WHERE registration_state = 'pending_approval' AND deleted_at IS NULL) THEN
    RAISE EXCEPTION 'a sign-up is waiting for approval: approve or reject it first';
  END IF;
END $$;
-- 0043 down
DROP INDEX IF EXISTS idx_users_registration_pending;
ALTER TABLE users DROP COLUMN IF EXISTS registration_state;
ALTER TABLE organizations DROP COLUMN IF EXISTS registration_email_domains, DROP COLUMN IF EXISTS registration_verify_email;
DROP TABLE IF EXISTS instance_settings;
DELETE FROM goose_db_version WHERE version_id = 43;
COMMIT;
SQL
cp docker-compose.v0.8.2.yml docker-compose.yml
docker compose up -d
```

Sessions and tokens carry over. Self-registered accounts stay as ordinary
`org_user` accounts; one that never verified its email is refused at
sign-in by `v0.8.2`, which requires a verified email of every user. Issued
claim links stay in the database; `v0.8.2` redeems none (it requires an
inactive organization). Restore the step-1 dump only if the database itself
must go back; that loses everything written after it.

## Known limitations

- **The browser logs two expected answers.** The sign-in page's
  organization lookup answers 404 for an email domain that is no
  organization's (the sign-in continues at the password step), and a
  pending self-registrant's refused sign-in answers
  `403 registration_pending`; neither is covered by
  `X-Identuum-Login-Step-Status`.
- **Requiring a verified email needs SMTP**; without it the setting is
  refused (`400 smtp_not_configured`) and the console disables it.
- **A claim link needs `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**; without it
  nothing is issued (`409 claim_url_unavailable`).
- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions.
- **The step-status opt-in is OSS's.** identuum-idp-ce does not honour
  `X-Identuum-Login-Step-Status` yet.
- **Compose over IPv6** is documented, not yet proven on a Linux Docker
  host.
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is
  a Professional+ capability.
