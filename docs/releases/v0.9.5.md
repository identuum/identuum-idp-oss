# identuum-idp-oss v0.9.5 — release notes

Tag `v0.9.5` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.5`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.5`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`4ff1270`.

## Changes

This release finishes the security review that `v0.9.4` began: the findings
that waited for an owner decision, and the ones found while reviewing
`v0.9.4`. Each fix has a test that failed first. The details are in
`CHANGELOG.md` (`## v0.9.5`); what matters to an operator:

- **Who edits an organization.** A tenant organization's domain and policy
  (MFA, sign-in and API authorization policy, registration, sessions,
  password rules, service-account expiry, M2M anomaly limits, strict
  re-authentication, local-admin-only) belong to its own org admin. A site
  administrator changes only its name and whether it is active; anything
  else answers `403 forbidden_field`. The org admin never changes whether
  the organization is active. The System organization is unchanged. In the
  console, the site administrator's form shows only the name and the active
  switch, and the org admin's settings page sets the name and the MFA policy.
- **Org admins restore deleted users** of their own organization, and see and
  replay the back-channel logout deliveries of their own organization's apps.
  A site administrator still lists every delivery, but sees the user and
  session ids only for the System organization's apps.
- **A lost second factor of the last org admin** is reset on the host with
  the new `reset-org-admin-mfa` command. It removes the admin's
  authenticator, recovery codes and passkeys, ends the admin's sessions and
  is audited. See `docs/OPERATOR-GUIDE.md`.
- **Sign-in.** After 5 failed sign-ins for one account in 15 minutes, from any
  address, the next attempt waits 1 second, then 2, 4 and so on up to 60
  seconds (`429 login_throttled` with `Retry-After`). The account is never
  locked. `/authorize` gives no code to an app not registered for the code
  grant. A second upstream sign-in in one browser no longer voids the first.
- **Tokens.** An app's access token no longer carries the user's role.
- **Second factors.** The wrong-code budget of the proof routes (step-up,
  MFA disable, recovery-code regeneration, skip consent) is kept in the
  database, so a restart does not reset it.
- **Apps and resources.** A deleted organization releases its API
  resources' audiences, and restoring it brings them back when they are
  still free. An RFC 7592 client update keeps the initial access token's
  limits (no shipped binary mounts that route yet).
- **Operators.** The setup banner names the binary's path; shutdown waits
  for mail sent after a response; the untrusted-proxy warning keeps naming
  new peers; self-registration answers take the same minimum time.

## Upgrading from v0.9.4

Three migrations (`0048` to `0050`) run on start. No route was removed or
renamed, and the endpoint count stays 157. The database, the data volume,
the URL, browser sessions and issued tokens carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.4.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.4-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.5/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for administrators and clients:**
   - **Organization policy:** a script or tool that changed a tenant
     organization's policy or domain as the site administrator now gets
     `403 forbidden_field`. Make the change as that organization's org admin.
     An organization with no org admin keeps its policy until one is
     appointed.
   - **Sign-in clients** that retry a failed password quickly see
     `429 login_throttled`; wait `Retry-After` seconds.
   - **Apps that read `role`** from an access token or from `userinfo` no
     longer find it in a token issued to an app. Console sessions keep it.
   - **Apps registered without `authorization_code`** among their grant
     types no longer receive a code from `/authorize`
     (`unauthorized_client`).
   - **An upstream sign-in in progress** while the server restarts must be
     started again.

## Upgrading from v0.9.3 or earlier

Follow the `v0.9.4` notes first: migration `0045` (in `v0.9.4`) stops if two
API resources share an audience, and it runs before `0050`, so a resource of
an organization that was already deleted still counts. This query shows each
shared audience and whether its organization is deleted:

```sql
SELECT r.audience, r.id, o.name, o.deleted_at IS NOT NULL AS organization_deleted
FROM api_resources r JOIN organizations o ON o.id = r.org_id
WHERE r.audience IN (SELECT audience FROM api_resources GROUP BY audience HAVING count(*) > 1)
ORDER BY r.audience, organization_deleted DESC;
```

A resource whose organization is deleted can be removed with
`DELETE FROM api_resources WHERE id = '<id>';` (its scopes go with it).
Rename or delete the others as the `v0.9.4` notes say, then upgrade.

## Rolling back to v0.9.4

Three migrations were applied, and v0.9.4 has not been run against a v0.9.5
database. To go back, restore the compose file and the step-1 dump:

```bash
docker compose down
cp docker-compose.v0.9.4.yml docker-compose.yml
# restore identuum-idp-v0.9.4-backup.sql into the database, then:
docker compose up -d
```

That loses everything written after the dump.

## Known limitations

- **Requiring a verified email needs SMTP**; without it, the setting is
  refused (`400 smtp_not_configured`).
- **A claim link needs `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**; without it,
  nothing is issued (`409 claim_url_unavailable`).
- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions.
- **Single replica.** OSS runs one serving instance (a DB lease); HA is a
  Professional+ capability.
- **The console sets two organization fields.** The org admin's settings
  page sets the name and the MFA policy; the other policy fields are set
  through `PUT /api/v1/organizations/:id`. The console has no view of
  deleted users yet, so a restore is made through
  `POST /api/v1/users/:id/restore`.
- **Mail after the response.** The reset, resend and registration mails are
  sent after the answer, so they arrive a moment after it.
