# identuum-idp-oss v0.6.0 — release notes

Tag `v0.6.0` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.6.0`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. identuum-ui `v0.3.0` is the UI
this binary embeds; identuum-idp-ce follows on its own track.

## Theme: one binary serves the UI and the API

Until `v0.5.x` an install ran two application containers: `identuum-idp` on
`:7113` and the Next.js `identuum-ui` on `:7104`, which proxied the browser's
API calls. From `v0.6.0` the binary embeds the identuum-ui static export
(identuum-ui `e5df81c`, tag `v0.3.0`, tree digest
`0683e5a3bae74ea27812dbf2d75d2c9519217d5e291134eb362a5c5832509614`, checked
at every build by `make ui-vendor-check`) and serves it on the issuer's own
origin. The issuer, the UI's public URL and the allowed browser origin are
one origin: `http://localhost:7113` in the compose file.

The browser talks to the API through a narrow boundary under `/bff`:

- It lifts the HttpOnly `access_token` cookie into a Bearer for `/api/v1/`
  only, never forwards the Cookie header, and forwards only a canonical path.
- Every request, safe methods included, needs `X-Requested-With:
  identuum-ui` and an `Origin` that is this host or an allowlisted origin;
  Fetch Metadata that says cross-site is refused (owner decision D1).
- `/bff/session/refresh` rotates the refresh cookie into new HttpOnly
  cookies and returns no token. Two concurrent refreshes, on one process or
  on two processes sharing the database, mint exactly one successor.
- `/bff/session/logout` revokes the session and says `local_only` when the
  server could not confirm the revocation; the cookies are cleared either
  way.
- The resource API accepts a Bearer only: a cross-site request that carries
  only cookies is refused with `401` (owner decision D4, proven, no code
  change).

Other changes:

- The `refresh_token` cookie is scoped to `Path=/bff/session/` (owner
  decision D3): the browser sends it to the boundary's refresh and logout
  and nowhere else. Clearing it expires it there and at the `Path=/` that
  earlier releases set.
- `POST /api/v1/auth/session/refresh` answers a session-store outage with
  `503 refresh_unavailable` and rotates nothing (owner decision D2);
  refresh and logout refuse with `503` rather than claim a revocation they
  could not confirm.
- `GET /api/status`, `GET /api/runtime-config` and `/healthz` answer from
  the binary when the UI is mounted.
- `identuum-idp healthcheck [base-url]` exits 0 only when the server's own
  `/healthz` answers 200. The compose file uses it as the Docker
  healthcheck, since the distroless image has no shell.

No migration (`0001`–`0040`, as in `v0.5.1`), no dependency moved, Go
1.27.1. The canonical endpoint count is 144, unchanged
(`go run ./tools/api-docgen --dry-run | grep -c '^  - id:'`). The full list
is in `CHANGELOG.md`, `## v0.6.0`.

## Upgrading from v0.5.x

The database and the data volume carry over unchanged. What changes is the
address, the number of containers, and the browser sessions.

1. **Back up.** Keep a copy of the current compose file and dump the
   database:

   ```bash
   cp docker-compose.yml docker-compose.v0.5.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.5-backup.sql
   ```

2. **Stop the old stack without `-v`.** This removes the `identuum-idp-oss`,
   `identuum-idp-oss-ui` and `identuum-idp-oss-postgres` containers and keeps
   the volumes `identuum-idp-oss-postgres-data` and `identuum-idp-oss-data`:

   ```bash
   docker compose down
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **Replace the compose file with the `v0.6.0` one and start it.** It has
   no `identuum-ui` service; nothing else about your volumes changes:

   ```bash
   curl -fsSLO https://downloads.identuum.com/idp-oss/docker-compose.yml
   docker compose up -d
   ```

   If you edited the old file (a bind address, a key), carry those edits
   over. `IDENTUUM_UI_BIND_ADDRESS` no longer exists; `IDENTUUM_IDP_BIND_ADDRESS`
   binds the one published port.

4. **Open the new URL: `http://localhost:7113`.** `:7104` no longer answers.
   - Update bookmarks and any links you handed out from `:7104` to `:7113`.
   - A **reverse proxy** that sent the UI host name to `:7104` and the API
     host name to `:7113` now sends one host name to `:7113`. The binary
     refuses browser requests from any origin but its own, so the public URL
     you open must be the issuer: set `IDENTUUM_IDP_OSS_ISSUER` and
     `IDENTUUM_IDP_UI_PUBLIC_BASE_URL` to that one public URL.
   - Activation links issued before the upgrade point at the old UI URL;
     re-issue them.

5. **Users may have to sign in again.** Browser cookies are bound to the host
   name, not the port. A browser that reaches `v0.6.0` on the same host name
   it used for the old UI (for example `localhost:7104` → `localhost:7113`)
   keeps its session: it refreshes through `/bff/session/refresh`, and its
   first logout expires both the old `Path=/` refresh cookie and the new one.
   A browser that reaches `v0.6.0` on a different host name has no session
   there and signs in again with the same password and second factor.
   Accounts, organizations, clients, roles and enrolled authenticators are
   unchanged.

The `identuum-idp-oss-ui` container is removed by step 2. If you upgraded
with `docker compose up -d` over the old file instead, remove the leftover
UI container with `docker compose up -d --remove-orphans`.

## Rolling back to v0.5.1

`v0.6.0` adds no migration, so a `v0.5.1` binary reads the same database.

```bash
docker compose down
cp docker-compose.v0.5.yml docker-compose.yml
docker compose up -d
```

Open `http://localhost:7104` again. A session made under `v0.6.0` keeps
working only until its access cookie expires (at most 15 minutes): `v0.5.1`
does not see the `Path=/bff/session/` refresh cookie, so users then sign in
again. Data written under `v0.6.0` stays.
If the database itself must go back, restore the step-1 dump into a stopped
install; that loses everything written after the dump.

## Known limitations

- **The published image does not record its commit.** `publish-image.yml`
  passes `VERSION` but no `COMMIT` build argument, so the image's build
  commit is the Dockerfile default `unknown`. The tag, the `sha-<commit>`
  image tag the workflow also pushes, and the provenance attestation still
  name the commit.
- `publish-image.yml`'s header comment still describes the UI on `:7104`.

## Verification

- Red first, then green: `cmd/identuum-idp`
  `TestHealthcheck_ExitsZeroOnlyWhenHealthzAnswers200` (red: `unknown
  subcommand "healthcheck"`, exit 2) and
  `TestHealthcheckTarget_FollowsTheApplianceListenAddress`; `internal/handlers`
  `TestD3_RefreshCookieReachesOnlyTheBFFSessionRoutes` (red: "the browser
  sends refresh_token to /; D3 scopes it to /bff/session/") and
  `TestD3_ClearExpiresTheScopedAndTheLegacyRootRefreshCookie`.
- Database proofs (`internal/e2e`, Postgres): the browser refresh race has
  one successor, reuse after grace revokes the family, a store outage is
  `503` with no rotation, logout confirmed versus unconfirmed.
- Two processes, one database (`IDENTUUM_IDP_ALLOW_MULTI_REPLICA=true`): 25
  rounds of the same refresh cookie sent to both processes at once, each
  round exactly one successor, and the session never revoked as reuse.
- `make verify` and CI on the pushed head are recorded with the publication.

and a session survives it only on the same host name; the API is unchanged.
