# identuum-idp-oss v0.9.14 — release notes

One email address is one account on the whole server, every sign-in now asks
for the password change an administrator requested, organization audit views
show the events that concern the organization, and two setup runs at once no
longer make two signing keys. The release embeds identuum-ui
`0b8d4a4`
(`0b8d4a403b36d7600530941173f1dfb397805020`, export tree digest
`1ee3f32a0280868338a093989bdcd2bfe611f3fad1e120052126211f0d2648f8`). The identuum-ui `v0.9.14` tag is created on that
revision at publication.

This page traces the changes in `v0.9.13..3e1050f`:
33 commits (`git rev-list --count v0.9.13..3e1050f`,
measured before this notes update). The release tag commit, its Linux image
index digest and its binary hashes are published with the release. Image publication uses
`publish-image.yml` on the release tag with `latest_tag: false`. Binary
publication uses `publish-binaries.yml` on the same tag.

## What changes for you

- **Before you upgrade, check for one email address on two live accounts.**
  Migration 0056 refuses the upgrade while such a pair exists. Run
  `identuum-idp audit-preupgrade <database-url>` with the v0.9.14 binary
  first (see "Upgrading from v0.9.13").
- **If you set passwords for members who also use a passkey or a provider:**
  those sign-ins now ask for the new password first, and an administrator-set
  password older than 24 hours that was never changed stops them. Give such a
  member a reset link.
- **If you are an organization administrator:** your audit view now shows
  more of the sign-in, token, consent, logout and step-up events of your
  members. Old rows are not changed.
- **If you integrate with the user API:** a duplicate address in the same
  organization on `POST /api/v1/users` now answers `409 email_exists`, not
  `400 invalid request`.
- **If you run `recover-site-admin`:** each reset now writes an audit record,
  and the command exits non-zero when that record cannot be written.

## Changes

The full list, with the exact wording of every response, is the `v0.9.14`
section of [CHANGELOG.md](../../CHANGELOG.md). In short:

### Accounts and sign-in

- **One email address, one account across the server.** Organization create
  with `admin_email`, user create, invite, bulk create and email update
  refuse an address that a live account anywhere holds, in any case
  (`409 email_exists`; bulk reason `email already exists`). A first sign-in
  through an organization's identity provider with such an address is sent
  to `/login?reason=sign_in_not_permitted` and nothing is created; an
  organization claim is refused. New addresses are stored trimmed and
  lowercased; addresses stored before v0.9.14 keep their case.
- **Sign-in by email finds the account in any case.** Passkey sign-in,
  password sign-in, password reset, the verification re-send and the
  in-organization provider lookup trim and lowercase the typed address and
  compare it in lower case. Older mixed-case accounts are found. Stored
  addresses are not changed; the passkey ceremony is unchanged.
- **A held address gets the held-address answer.** Self-registration with an
  address held by a banned account or by an account in an inactive
  organization now takes the address-in-use path (`existing_email`, the
  notice mail, the same `202`), not `create_failed`.
  `POST /api/v1/users/:id/restore` of a deleted user whose address another
  live account now holds answers `409 email_exists` (was `500`); the user
  stays deleted.
- **Passkey and provider sign-in ask for the required password change.**
  `POST /api/v1/auth/login/webauthn/finish` answers as password sign-in does:
  `401 password_change_required` with the one-time `session_id` for
  `POST /api/v1/auth/login/password-change`, or `401 password_expired`. A
  provider sign-in, for the console or for an application, redirects to
  `/login?reason=password_change_required` or
  `/login?reason=password_expired` before the provider identity is linked.
  No session, refresh token or cookie exists before the member chooses a
  password. A member with no local password (an account the provider owns,
  or an `idp_only` organization's member) is never asked for one.
- **Sign in again after your session ends.** If your application still sends
  the old session token, it no longer blocks the normal sign-in steps. You
  must still complete sign-in. The old token does not restore your session
  or grant access to protected pages. This fix does not cover expired or
  revoked tokens rejected before the session check.

### Organizations, providers and mail

- `POST /api/v1/organizations/:id/identity-provider` with a `priority` other
  than `0` answers `400 priority_not_supported`, and nothing is created (it
  answered `201` and stored `0`). No priority, or `0`, works as before.
- The re-sent invitation and the organization activation mail name the
  organization in the subject and in the first line.
- `POST /api/v1/agent-communication-authorizations` holds both service
  accounts and both clients while it saves and checks them again; an owner
  transfer that runs beside a create waits. No answer changed.

### Audit

- **Organization attribution.** Organization audit views include newly
  written events for recovery-code sign-in, required MFA and password-change
  steps, session refresh, browser sign-in, tenant token issuance, known-user
  step-up failures, cookie logout, authorization-code issuance, consent
  decisions, client token revocation, verified passkey sign-in and step-up,
  refresh-reuse refusals, browser MFA enrollment outcomes, final-mint
  failures, pending-MFA storage failures, browser authorization refusals with
  a known member and authenticated-client communication refusals. Failure
  attribution uses the member or client the server resolved; submitted
  identifiers alone never assign an organization. The tenant clamp still
  excludes other organizations and server-wide events.
- **Global relying parties.** A back-channel logout delivery by a global
  relying party now belongs to the verified tenant member's organization, so
  that organization's administrator sees it. A delivery with no known tenant
  member stays server-wide and only site administrators see it.
- **`recover-site-admin`** records `site_admin_credentials_reset` (actor
  `system`, `via: cli`, the system organization) with `sessions_revoked` and
  `refresh_tokens_revoked_count`; `success` only when both revocations
  completed, else `failure`. It never records the password, its hash or the
  environment value. A refused run records nothing. The console's event-type
  filter lists the new type.
- The audit rows `user_session.login.password_change_required` and
  `user_session.login.password_expired` carry `metadata.method`
  (`password`, `passkey` or `oidc_upstream`; plus `provider_id`).
- Existing audit rows are not rewritten and keep their earlier visibility.

### Setup and bootstrap

- Two setup completions at once (two replicas, or a retry while the first
  request still runs) now leave one signing key: setup creates its first key
  under the database lock that startup key provisioning uses (v0.9.11). The
  second completion reuses the key and still succeeds. Setup stays
  single-use; a key store error still refuses and leaves setup open.
- `identuum-idp bootstrap` takes the same lock. When another run has just
  made the key it prints `signing key already present` naming that key.

### Operator tools

- `audit-preupgrade` reports the addresses that stop migration 0056: the
  count, and per address the user ids and organization ids (never the
  address); it exits `1` while any exist.
- `migrate` exits `3` when a migration refused the stored data and changed
  nothing (`0` current, `1` could not run). On exit `3` the appliance keeps
  running NOT-SERVING (`/health` names the schema version) until the data is
  fixed and the container restarts.

### Console (identuum-ui `0b8d4a4`)

- Invite user shows "This email address already has an account. Use another
  address." for `email_exists`.
- Passkey sign-in opens the password-change step when one is owed, and shows
  the expiry words for an expired administrator-set password; the sign-in
  banner has words for the two new provider refusal reasons.

### Fixed known issues of v0.9.13

- One email address in two organizations stopped email sign-in for both
  accounts — fixed (one address per server, migration 0056).
- A passkey or provider sign-in did not ask for the password change an
  administrator requested — fixed.
- A re-sent invitation or activation email did not name the organization —
  fixed.

## Upgrading from v0.9.13

This release adds one SQL migration, `0056_users_email_global_unique.sql`.
The tracked `migrations/` directory contains 56 SQL files, head `0056`
(`git ls-files 'migrations/[0-9][0-9][0-9][0-9]*.sql' | wc -l`, measured 56
at 9f1f671). No route is added or removed; the endpoint count stays 166
(`grep -c . tools/api-docgen/testdata/endpoints.manifest.txt`, measured 166
at 9f1f671). No new setting.

- 0056 adds a database rule: at most one live (not deleted) account per
  `lower(email)`. A soft-deleted duplicate does not count.
- **If the database already holds a live duplicate (across organizations, or
  in case only), 0056 refuses and changes nothing.** The schema stays at
  0055, `migrate` exits `3`, and the appliance serves NOT-SERVING.

1. Back up the database, the Compose file and the matching encryption key,
   as `docs/OPERATOR-GUIDE.md` says.
2. Run `identuum-idp audit-preupgrade <database-url>` with the v0.9.14
   binary, or the read-only SQL query in the operator guide ("Before
   upgrading to v0.9.14: one email address, one account"). No duplicate
   means go ahead. For each duplicate, keep one account and give each other
   account its own address (`PUT /api/v1/users/{id}` with `email`) or delete
   it (`DELETE /api/v1/users/{id}`), on v0.9.13, until none is left.
3. Pull the digest-pinned v0.9.14 Compose file and start it. The migration
   runs at start.
4. Check `/readyz` and sign in.

If an upgrade was already refused: fix the duplicates as in step 2, then
restart the container (or run `identuum-idp migrate` again); the migration
then applies.

After the upgrade, behaviour that changes without any action:

- Members with a pending administrator-set password who sign in with a
  passkey or a provider are sent to the password-change step; an
  administrator-set password older than 24 hours stops those sign-ins. Give
  such members a reset link.
- An application or console that handles provider refusals by
  `/login?reason=<code>` meets two new codes, `password_change_required` and
  `password_expired` (closed list in `docs/guides/oidc-upstream-login.md`).
- Organization audit views gain the events listed under "Audit" from the
  upgrade on; rows written before it keep their earlier visibility.

## Rolling back to v0.9.13

The v0.9.13 server refuses the newer schema. Restore the verified
pre-upgrade backup into an empty database before you start v0.9.13; all
changes since the backup are lost. This is backup and restore, not an
in-place migration-down procedure. A refused 0056 changed nothing, so a
server whose upgrade was refused can go back to the v0.9.13 image on the
same database.
