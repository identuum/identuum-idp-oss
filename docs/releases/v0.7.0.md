# identuum-idp-oss v0.7.0 — release notes

Tag `v0.7.0` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.7.0`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.7.0`, `dry_run: false`). The
binary embeds identuum-ui `55af159` (tree digest
`20950ed95cf47bad23bf215665e4ca1bcee70738c23c4adf54673e18fb4eebf6`), the
tree identuum-ui `v0.4.0` publishes.

## Theme: an organization admin can add users without mail

`v0.7.0` makes the no-SMTP install — the default — a complete one: every
account an administrator creates is handed over as a one-time link (owner
ruling D-016), and email, where configured, is only a second way to deliver
it.

- **Invite a user.** In the console, **Users → Invite user** (email, name,
  Member or Admin) creates the user *pending* and shows a one-time link, its
  token and its expiry, once. The user sets their own password at `/invite`
  and signs in; MFA follows the organization's policy. A pending user reads
  **Invitation pending**, and **Re-issue invitation** retires the previous
  link. With SMTP the link is also mailed. The same over the API:
  `POST /api/v1/users` without a password, `POST /api/v1/users/:id/invite`,
  and the public `GET /api/v1/auth/invite/:token` and
  `POST /api/v1/auth/invite` (rate-limited like sign-in).
- **Activation works without mail.** The organization activation link opens
  `/activate` on a no-SMTP install; in `v0.6.x` that page said it was not
  available. A lost link is re-issued from the organization's page
  (**Re-issue activation link**), which retires the earlier one.
- **The container reports unhealthy when the database is unreachable.**
- **The image names its commit** (`identuum-idp version`).
- **Linux binaries.** The release ships the bare binary for `linux/amd64` and
  `linux/arm64` (`identuum-idp-oss_0.7.0_linux_<arch>`), a `SHA256SUMS` over
  both and a build-provenance attestation for each (`gh attestation verify`).
  The binary alone runs the product, UI included, on a PostgreSQL 18+
  database (README, "Running the bare binary").

The full list is in `CHANGELOG.md` (`## v0.7.0`).

## Upgrading from v0.6.3

Measured against `v0.6.3`: no migration (the schema stays
`0001`–`0040`), `go.mod` and `go.sum` unchanged. The database, the data
volume, the URL and the browser sessions carry over.

1. **Back up** the compose file and the database, as for `v0.6.3`:

   ```bash
   cp docker-compose.yml docker-compose.v0.6.3.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.6.3-backup.sql
   ```

2. **Replace the compose file and recreate the container:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.7.0/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **What changes for clients and operators:**
   - **New routes** (canonical endpoint count 144 → 147):
     `POST /api/v1/users/:id/invite`, `GET /api/v1/auth/invite/:token`,
     `POST /api/v1/auth/invite`. `POST /api/v1/users` without a password now
     creates a pending user and answers the invite; with a password it is
     unchanged.
   - **Capabilities** in `GET /api/v1/component`: `user_invite` and
     `activation_link` (both `true` on OSS). Users carry `invitation_pending`.
   - **Health:** a new unannotated `GET /readyz` (503 when the database does
     not answer); `identuum-idp healthcheck` — the image's Docker
     HEALTHCHECK — now requires `/healthz` and `/readyz`. `/health` and
     `/healthz` stay liveness.
   - **Bare binary only:** with `IDENTUUM_IDP_DATA_DIR` unset the setup code
     goes to `<user config dir>/identuum-idp`, no longer the working
     directory. The image keeps `/app/data`.
   - **Audit events:** `user.invited`, `user.invite_reissued`,
     `user.invite_redeemed`; `setup.completed` and `user_created` at setup;
     `user_deactivated` / `user_activated` (with the actor) for a disable or
     enable, where `v0.6.3` wrote a bare `user.updated`;
     `oauth_authorize.code_issued` also for a code approved on the consent
     page.
   - **Logs:** an invite or activation not mailed because SMTP is not
     configured logs at Info ("not mailed: delivery not configured"), no
     longer WARN. One-time tokens in a request path
     (`/api/v1/auth/invite/:token`,
     `/api/v1/auth/organizations/activate/:token`) are recorded as the route
     template in log lines and audit rows.
   - **Site-admin organization state:** a pending administrator with a valid
     activation reads *Admin active*; `can_assign_admin` becomes `true` only
     once the activation has expired (in `v0.6.3` it was `true` for any
     pending administrator). A restored organization's
     `GET /api/v1/organizations/:id/admin-recovery-candidates` answers 200.
     `PUT /api/v1/organizations/:id` with `{"active":true}` on an
     organization whose administrator has never activated answers `409
     activation_pending` and changes nothing: the administrator's activation
     link activates it (re-issue it with **Re-issue activation link** on the
     organization's page, or `POST /api/v1/organizations/:id/resend-activation`).
     In `v0.6.3` the
     organization was switched on without its administrator, whose link then
     failed. A shell organization, or one whose administrator has activated,
     reactivates as before.

## Rolling back to v0.6.3

`v0.7.0` adds no migration, so a `v0.6.3` binary reads the same database.

```bash
cp docker-compose.v0.6.3.yml docker-compose.yml
docker compose up -d
```

Sessions carry over. Users still pending an invitation stay pending (their
links do not work under `v0.6.3`, which has no invite routes); users who
redeemed keep their passwords. Restore the step-1 dump only if the database
itself must go back; that loses everything written after it.

## Known limitations

- **No first verification mail for password-created users.** A user created
  *with* a password (or a self-registrant) is unverified and receives no
  first verification link; `POST /api/v1/auth/resend-verification` sends one
  when SMTP is configured. Invited users are verified when they redeem.
- **Most audit rows carry an empty `actor_type`.** The new events above name
  their actor; older events do not yet.
- **An org_admin's audit view is narrow:** it shows few of the
  organization's events (not its `user.*` and `org_role.*` events).
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is a
  Professional+ capability.
- **Separate sessions.** The console and the OpenID Connect sign-in
  (`/api/v1/auth/browser-login`) keep separate sessions: signing in to one
  does not sign in to the other, and `end_session` does not sign the console
  out. Without a `post_logout_redirect_uri`, `end_session` answers `204` with
  no page.
