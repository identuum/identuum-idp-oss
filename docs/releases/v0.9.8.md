# identuum-idp-oss v0.9.8 — release notes

Tag `v0.9.8` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.8`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.8`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`d009997`.

## Changes

The details are in `CHANGELOG.md` (`## v0.9.8`); what matters to an
operator:

- **Service-account expiry works.** An organization's "Service account
  expiry (days)" is applied: a service account created without an expiry
  date expires that many days after it is created. `0` means no default
  expiry. A date you set is kept, and accounts that already exist do not
  change. If the IdP cannot read the organization's value, it does not
  create the account.
- **New organizations start with the expiry off** (`0`), unless the create
  request names a value. The org_admin turns it on in the console:
  **Settings → Service accounts** (1 to 3650 days).
- **An API resource can check its own tokens.** A `client_credentials`
  token requested with `audience=<the API resource>` is now active when that
  API resource introspects it, if the resource and the token belong to the
  same organization, and to the client it was issued to. Every other caller
  still gets `{"active":false}`. Such a token is still refused as a bearer
  on the IdP's own API and at userinfo.
- **The console page runs only its own scripts and sends no referrer.**
  The page the browser loads now carries a `Content-Security-Policy` that
  allows only this server's scripts, styles and requests, and
  `Referrer-Policy: no-referrer`, so the one-time link in `/claim`, `/invite`
  and `/reset-link` is never sent on in a `Referer` header. API responses
  keep their headers. A reverse proxy in front of the IdP must pass these
  headers through unchanged (OPERATOR-GUIDE, "Security headers").
- **Console:** sign-in sends the browser to single sign-on only on this
  server's own sign-in route, and a new organization's activation link is a
  link only when it is `https` or on the console's own address; otherwise it
  is shown as text to copy.

## Upgrading from v0.9.7

One migration runs at start: `0051` changes the default of
`organizations.service_account_expiry_days` to `0`. No row changes. No route
was added, removed or renamed; the endpoint count is 159. The database, the
data volume, the URL, browser sessions and issued tokens carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.7.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.7-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.8/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for clients:**
   - **Introspection** answers `active: true` to an API resource for a token
     whose `aud` names that resource (it answered `active: false`).
   - **A service account created without `expires_at`** gets one, when its
     organization's value is above `0` (it never expired). Check each
     organization's value in the console before you upgrade: an organization
     created before this release keeps the value it was created with.
   - **A new organization** starts at `0` when its create request names no
     value.
   - **A reverse proxy that injects an inline script** into the console
     page (an analytics snippet, for example) is refused by the new policy.

## Upgrading from v0.9.6 or earlier

Follow the `v0.9.7` notes first (and the earlier notes before them).

## Rolling back to v0.9.7

v0.9.7 starts on a database that v0.9.8 migrated (measured: it reports
"database at version 51" and serves). Restore the compose file and recreate
the containers:

```bash
cp docker-compose.v0.9.7.yml docker-compose.yml
docker compose up -d
```

After a rollback, new service accounts are no longer given the
organization's expiry (accounts already created keep the date they got),
API-resource tokens read inactive at introspection again, and the console
page loses its script policy and no-referrer. The column default stays `0`.
If you would rather return to the exact earlier state, restore the step-1
dump instead; that loses everything written after it.

## Known limitations

- **A public client gets no refresh token.** The refresh grant needs client
  authentication.
- **Step-up and the other second-factor proofs** take only an authenticator
  code, not a recovery code.
- **An enrolment started in Account settings** lives in the running process
  for its five minutes; after a restart the user starts it again.
- **A token minted for an API resource without an organization** (one an
  API resource requests for itself) is active only to the client it was
  issued to.
- **Resetting a user's password without email** is an API call
  (`PUT /api/v1/users/{id}`); the console has no button for it.
- **`IDENTUUM_IDP_TEST_ALLOW_PRIVATE_UPSTREAM_ISSUER`** turns the SSRF guard
  off for upstream sign-in; it is for tests only.
- **Requiring a verified email needs SMTP**, **a claim link needs
  `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**, **the console and the OpenID Connect
  sign-in keep separate sessions** (D-023), and **OSS runs one serving
  instance** — as in `v0.9.7`.

## Verification

`make verify-parallel`, the e2e mint, CI, the OpenID conformance run (both
plans against the committed floor), the upgrade from `v0.9.7` with data and
the rollback, the published image digest, the binaries and a smoke test of
the published compose file are recorded with the publication.

SemVer: `0.9.8` is a patch release, as `v0.9.4` and `v0.9.5` were with their
additive migrations. One additive migration (a column default); no route was
added, removed or renamed. Three answers change: introspection is active for
the API resource a token names; a service account created without
`expires_at` gets the organization's expiry; and a new organization's
`service_account_expiry_days` defaults to `0`.
