# identuum-idp-oss v0.8.2 — release notes

Tag `v0.8.2` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.8.2`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.8.2`, `dry_run: false`). The
binary embeds identuum-ui `0630183` (tree digest
`f1fd1583529a953841f4ca51b4d08ddf89835e3152d9a526d4e60303eee0e79a`), the
tree identuum-ui `v0.5.3` publishes.

## Theme: hardening — IPv4 by default, IPv6 by choice, a quiet console

- **IPv4 is the default; IPv6 is supported and opt-in** (D-020). The
  default listen `0.0.0.0:7113` (and `:7113`) is IPv4 only. `[::]:7113`
  listens on IPv6 (dual-stack where the OS allows); an IPv6 literal listens
  on that address only. The metrics listener follows the same rule (its
  default stays `127.0.0.1:9090`). The healthcheck probes `[::1]` for
  `[::]`. The compose file's `IDENTUUM_IDP_BIND_ADDRESS` takes an IPv6
  address; its header shows how to publish both families.
- **IPv6 clients are limited by their /64.** Rate limits and the sign-in
  lockout count an IPv6 client by its `/64` (IPv4 unchanged), so rotating
  addresses inside one `/64` no longer reaches a fresh limit.
  `IDENTUUM_IDP_TRUSTED_PROXIES` takes IPv6 CIDRs.
- **The console logs no error for an expected sign-in step.** A request
  sending `X-Identuum-Login-Step-Status: 200` (exact value) receives 200 with
  the same body, still no session, cookie or token, for the password step's
  `mfa_required` / `mfa_enrollment_required`, `password_change_required`,
  and the password-change step's MFA continuation; and `GET /api/v1/validate`
  and the browser refresh answer a caller presenting no credential 200
  `{"authenticated":false}`. Without the header every answer is unchanged; a
  credential that does not verify is still a 401. The embedded console
  sends it, so a signed-out visit to `/`, an MFA sign-in and a sign-in that
  must change its password log no browser console error.
- **Console and application sign-ins are separate** (D-023), written in the
  operator guide.
- **The development compose stack has its own names** (D-024):
  `deployment/docker-compose.dev.yml` uses `identuum-idp-oss-dev*`, so it and
  the production compose file can run on one host. The production compose
  file is unchanged.
- **The embedded UI** is identuum-ui `v0.5.3` (next 16.3.7).

## Upgrading from v0.8.1

No migration and no route, field or response shape removed or renamed.
Replace the image (or the binary) and start it; sessions and tokens carry
over.

- **The bare binary listens on IPv4 only by default.** In `v0.8.1` the
  default `0.0.0.0:7113` was dual-stack: it accepted IPv6 connections too.
  To keep IPv6, set `IDENTUUM_IDP_LISTEN='[::]:7113'` (or
  `--listen '[::]:7113'`). The compose install is unchanged: it already
  published IPv4 only.
- **IPv6 limits by /64.** Behind no proxy, IPv6 clients that share a `/64`
  now share one rate-limit and lockout budget.
- **Developers only:** the dev compose project is `identuum-idp-oss-dev`.
  Its database volume is project-scoped, so the first `make fast-up` after
  the upgrade starts an empty dev database, and a still-running pre-upgrade
  dev stack holds port 5513 until stopped.
  `IDENTUUM_IDP_COMPOSE_PROJECT=identuum-idp-oss` keeps the old stack.

## Rolling back to v0.8.1

Run the `v0.8.1` image (or binary) against the same database; nothing to
undo. With compose, put back the `v0.8.1` release's `docker-compose.yml`
asset (here saved as `docker-compose.v0.8.1.yml`):

```bash
curl -fsSL -o docker-compose.v0.8.1.yml https://github.com/identuum/identuum-idp-oss/releases/download/v0.8.1/docker-compose.yml
cp docker-compose.v0.8.1.yml docker-compose.yml
docker compose up -d
```

A bare `v0.8.1` binary on `0.0.0.0` listens dual-stack again. In-flight
rate-limit and lockout counters for IPv6 clients are keyed differently by
the two versions, so they start afresh after either change.

## Known limitations

- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions: signing in to one does not sign in to the
  other, and `end_session` does not sign the console out.
- **The step-status opt-in is OSS's.** identuum-idp-ce does not honour
  `X-Identuum-Login-Step-Status` yet; against it the console still sees,
  and the browser still logs, the 401s.
- **Compose over IPv6** is documented, not yet proven on a Linux Docker
  host.
- **Older audit rows** carry `organization_id` only where their metadata
  named the organization. The OSS log is plain and retention-pruned (30 days
  by default); it has no hash chain.
- **A console sign-in that fails** for a known email is recorded as
  `anonymous` (no password was proven).
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is
  a Professional+ capability.
