# identuum-idp-oss v0.9.12 — release notes

Truthful "email verified", safe concurrent client saves, a complete member
area and sign-in providers in Settings. The release embeds identuum-ui
`a932627` (`a932627f10cca17ee4c42f160f31bd4263e92693`, export tree digest
`93909681b7efc785d36ae75de5189b3b18f61aadc2044a5a8d7b9fc62314f7bf`). The
identuum-ui `v0.9.12` tag is created on that revision at publication.

This page traces the changes in `v0.9.11..cf1a22a`: 13 commits
(`git rev-list --count v0.9.11..cf1a22a`, measured before the notes
commit). The release tag commit, its Linux image index digest and its
binary hashes are published with the release. Image publication uses
`publish-image.yml` on the release tag with `latest_tag: false`. Binary
publication uses `publish-binaries.yml` on the same tag.

## What changes for you

- **If you run apps that read `email_verified`:** from this release it is
  true only for a mailbox the user proved (identuum's verification email)
  or the sign-in provider confirmed. New invited, link-activated,
  admin-created and setup users start with `false`. Users verified before
  the upgrade keep `true`. If an app needs `true`, ask those users to press
  "Send verification email" on their Overview page. That needs email (SMTP)
  configured on this server.
- **If you are an administrator:** the user page now says how each address
  was checked. Your hand switch still exists; it is shown as "Set by an
  administrator" and does not make the claim true.
- **If you are a member:** Overview shows your profile, two-step sign-in
  and devices, and lets you verify your address.
- **If two administrators edit the same OAuth client:** a save no longer
  undoes a change the other save made to a field it does not send. A save
  that cannot be stored answers `503` and changes nothing.

## Changes

The full list, with the exact wording of every response, is the
`v0.9.12` section of [CHANGELOG.md](../../CHANGELOG.md). In short:

### Clients (C1)

- A save of an OAuth client locks that one client while it is applied, so
  saves of the same client happen one after the other (`83a054f`). This
  covers `PUT /api/v1/clients/:id` and
  `POST /api/v1/clients/:id/secret/regenerate`.
- A service account bound in a save is locked and checked again under the
  lock; a deleted, deactivated or expired account answers `400` and
  nothing is saved (`727395b`).
- A save the database cannot complete answers
  `503 temporarily_unavailable` with `Retry-After`. A save on a client
  deleted meanwhile is refused. A save checked against an older view of the
  client is refused with a plain reason.

### Email verified (C2)

- The `email_verified` claim in ID tokens and userinfo is true only for a
  proven mailbox (`6d41444`). `users.email_verified_via` records how:
  `email_link`, `upstream_idp`, `legacy` (verified before v0.9.12; counts as
  proven), `admin_link`, `admin_set`, `setup`, or NULL (never proven).
- New signed-in route `POST /api/v1/me/email/verification`: a user asks
  for a verification email to their own address. It never returns the
  link. Without SMTP it answers `503 email_delivery_not_configured`; for
  the site_admin it answers `409 not_available_for_this_account`.
- Profile and admin user responses add `email_verified_via` and
  `email_proven`. `email_verified` there keeps its meaning, "account
  activated".
- A verification link proves only the address it was sent to (`024ecad`).
  An address change cancels the user's open links; a cancelled link
  answers `400 invalid_token`. The link is used and the proof is written in
  one transaction that holds the user's row (`0d97a5b`).
- A pending invitee who verifies by email keeps a working invite.

### Console (identuum-ui `a932627`)

- Member Overview without "Coming soon": Profile, Security and Sessions
  cards with real facts, and menu items for each.
- The email status says how the address was verified, and members can send
  themselves a verification email.
- Sign-in providers are listed and managed in Settings; Add, Edit and
  Remove return to the page.
- An expired sign-in is renewed before a save; distinct messages when the
  server does not answer.
- Clearer password, recovery-code and client-secret text; no "session
  expired" banner for visitors who never signed in.

## Upgrading from v0.9.11

This release adds two SQL migrations: `0053_users_email_verified_via.sql`
and `0054_email_verifications_address.sql`. The tracked `migrations/`
directory contains 54 SQL files, head `0054`
(`git ls-files 'migrations/[0-9][0-9][0-9][0-9]*.sql' | wc -l`).

- 0053 adds the nullable column `users.email_verified_via` with a check on
  the allowed values, and sets it to `legacy` for every user whose
  `email_verified` is true. No row loses access.
- 0054 adds the nullable column `email_verifications.email_hash` and
  cancels every unused verification link created before the upgrade,
  because those links do not record an address. Users who still need to
  verify ask for a new email.

One route is added; the endpoint count goes from 159 to 160
(`grep -c . tools/api-docgen/testdata/endpoints.manifest.txt`).

1. Back up the database, the Compose file and the matching encryption key,
   as `docs/OPERATOR-GUIDE.md` says.
2. Pull the digest-pinned v0.9.12 Compose file and start it. The
   migrations run at start.
3. Check `/readyz` and sign in. Users verified before the upgrade still
   show as verified.

## Rolling back to v0.9.11

The v0.9.11 server refuses the newer schema. Restore the verified
pre-upgrade backup into an empty database before you start v0.9.11; all
changes since the backup are lost. v0.9.11 sends `email_verified: true`
again for invited and admin-created users. This is backup and restore, not
an in-place migration-down procedure. Do not roll back past 0053 and
upgrade again after users were created on v0.9.12: running 0053 again
marks every activated user `legacy`, which counts as proven.

## OpenID Connect conformance

The conformance run for this release is recorded with the release
revision; it is pending at the time of this commit. The email scope module
checks that `email_verified` is present and boolean; it does not require
`true`. This is not a certification claim.

## Known limitations

- On a server without email, invited and admin-created users cannot become
  "verified"; the console says so.
- The Applications card (apps a member allowed) is not in this release.
- The console's application form sends six fields on every save: the name,
  the redirect URIs, the post-logout redirect URIs, the allowed audiences,
  the scope and "skip consent". For those six fields, the save that
  arrives last still wins, even from a form opened earlier. The lock
  protects the fields a save does not send: PKCE, the secret, the service
  account, the logout and token settings, and changes made through the API.
- [KNOWN_ISSUES.md](../../KNOWN_ISSUES.md): the v0.9.11 email-verified
  entry is fixed in this release.
