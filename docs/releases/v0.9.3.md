# identuum-idp-oss v0.9.3 — release notes

Tag `v0.9.3` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.3`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.3`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`9cfd09b`, as `v0.9.2` did.

## Changes

- **Security hardening.**
  - The sign-in `return_to` target and the step-up pages accept only a
    local path.
  - Consent "deny" redirects only to a registered redirect URI.
  - A registered redirect URI may not carry a fragment or userinfo, and
    must use https unless its host is loopback.
  - A PKCE `code_verifier` must have the RFC 7636 shape: 43 to 128
    unreserved characters.
  - `private_key_jwt` client assertions are bounded from the current time,
    and their replay record lasts until they expire.
  - An admin who sets a user's password ends that user's sessions and
    refresh tokens.
  - A completed password reset retires the user's other reset links.
  - The organization-activation link redeems only for an org admin who
    has not activated. The activation resend refuses an admin who already
    did (`409`).
  - Passkey sign-in fails closed (`503`) when the organization policy
    cannot be read.
  - Outbound fetches (upstream OIDC, JWKS, back-channel logout) follow
    redirects only for GET, only to https on the same host, at most three
    times.
  - The appliance refuses an encryption-key file that is not a regular
    file.
  - Client-secret regeneration no longer returns internal error text.
  - Logs carry user ids instead of email addresses, and redact one-time
    tokens in `/bff/...` paths.
- **Deployment.**
  - The published compose file pins PostgreSQL by digest.
  - `deployment/README.md` says how to change the database password.
- **Third-party notices ship.** `THIRD_PARTY_NOTICES` is embedded in the
  binary (`identuum-idp licenses`) and carried in the image at
  `/app/THIRD_PARTY_NOTICES`.
- **Project.**
  - `CONTRIBUTING.md` and issue forms are added.
  - Maintainer material moved to `docs/maintainers/`.
  - CI runs with a read-only token and installs grype from a
    checksum-verified archive.
  - The release workflows refuse a dispatch ref other than the tag.

The full list is in `CHANGELOG.md` (`## v0.9.3`).

## Upgrading from v0.9.2

No migration. `go.sum` gains one module, used only by the notices tool,
not by the binary. No route was removed or renamed, and the endpoint count
stays 157. The database, the data volume, the URL, browser sessions and
issued tokens carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.2.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.2-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.3/docker-compose.yml
   docker compose up -d
   ```

   The PostgreSQL container is recreated from the pinned image (still
   PostgreSQL 18), and its data volume is kept. Never run
   `docker compose down -v`: it deletes the install's database.

3. **What can change for clients:**
   - **Redirect URIs:** an existing client whose redirect URI uses plain
     http on a non-loopback host, or carries a fragment, keeps working
     until its next edit. That edit is refused until the URI is made
     compliant.
   - **PKCE:** a client that sends a PKCE verifier shorter than 43
     characters, or with characters outside the unreserved set, now fails
     at the token endpoint.
   - **private_key_jwt:** a client whose assertions are dated in the
     future is refused.

## Rolling back to v0.9.2

The schema is the same, so restore the previous compose file and recreate
the containers:

```bash
cp docker-compose.v0.9.2.yml docker-compose.yml
docker compose up -d
```

Sessions and tokens carry over. Restore the step-1 dump only if the
database itself must go back; that loses everything written after it.

## Known limitations

- **Requiring a verified email needs SMTP**; without it, the setting is
  refused (`400 smtp_not_configured`).
- **A claim link needs `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**; without it,
  nothing is issued (`409 claim_url_unavailable`).
- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions.
- **Single replica.** OSS runs one serving instance (a DB lease); HA is a
  Professional+ capability.
