# identuum-idp-oss v0.8.0 — release notes

Tag `v0.8.0` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.8.0`, `latest_tag: false`); the index digest is
recorded where the compose file pins it. The Linux binaries are published
with `publish-binaries.yml` (`version_tag: v0.8.0`, `dry_run: false`). The
binary embeds identuum-ui `2e552be` (tree digest
`bf41513457ab23b76e55159a8e0f7f05ec52804dd26e392ccda16e38f83f7000`), the
tree identuum-ui `v0.5.0` publishes.

## Theme: sign-in and the audit log say what they mean

- **A user created with a password chooses their own at first sign-in**
  (owner ruling D-017). A user an administrator creates with a password
  (`POST /api/v1/users`, `/users/bulk`) is active and verified at once — the
  administrator vouches, audited — and by default must choose their own
  password before any session: the console answers
  `401 password_change_required` with a one-time `session_id`, redeemed at
  the new `POST /api/v1/auth/login/password-change`; the OpenID Connect
  sign-in shows the same step. Then MFA follows the organization's policy —
  and the browser sign-in now **enrols an authenticator app itself** when
  the policy requires one, instead of sending the user to the console.
  `must_change_password: false` lets the administrator's password stand.
- **First-party applications** (owner ruling D-018(b)). An organization
  admin marks its own confidential application **First-party (skip
  consent)**; `/authorize` then issues the code without the consent page
  (`prompt=consent` still asks), audited. A public client cannot be
  first-party (RFC 8252 §8.6; `400 invalid_request`).
- **Signed-out page** (D-018(a)). RP-initiated logout without a
  `post_logout_redirect_uri` shows the IdP's "You are signed out" page.
- **The audit log says who did what to which organization.** Every row
  names its actor (`user`, `service_account`, `client`, `setup_token`,
  `system`, or `anonymous` without one) and carries the organization acted
  upon; an organization admin's audit view lists every row of its
  organization, whoever acted — a site admin's changes included.
  `identuum-idp bootstrap` is audited like the setup wizard.
- **Earlier password-created users can be invited.** A user created with a
  password in `v0.7.0` or earlier is still unverified; **Send invitation**
  on the user's page (or `POST /api/v1/users/:id/invite`) lets them set a
  new password, which verifies the account.

The full list is in `CHANGELOG.md` (`## v0.8.0`).

## Upgrading from v0.7.0

Measured against `v0.7.0`: migrations `0041` (a pending sign-in kind) and
`0042` (`audit_events.organization_id`), both additive; `go.mod` and
`go.sum` unchanged. The image applies them on boot; the bare binary needs
`identuum-idp migrate "$IDENTUUM_IDP_DATABASE_URL"` before it starts. The
database, the data volume, the URL and the browser sessions carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.7.0.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.7.0-backup.sql
   ```

2. **Replace the compose file and recreate the container:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.8.0/docker-compose.yml
   docker compose up -d
   ```

   Never `docker compose down -v`: it deletes the install's database.

3. **What changes for clients and operators:**
   - **New route** (canonical endpoint count 147 → 148):
     `POST /api/v1/auth/login/password-change`.
   - **Users created with a password** from now on are verified and, by
     default, must change the password at first sign-in: a client of
     `POST /api/v1/auth/login` sees `401 password_change_required` with a
     `session_id` for them. Send `"must_change_password": false` on create to
     keep the old sign-in. A user already flagged `requires_password_change`
     is led to the change step (it used to be refused as
     `invalid_credentials`). **Users created with a password before
     `v0.8.0` are not changed**: still unverified; invite them to bring them
     in.
   - **Logout:** `/api/v1/oidc/logout` without `post_logout_redirect_uri`
     answers `200` with an HTML page (it answered `204` with no body). The
     redirect case, its `400` and the `204` for an unresolved client with a
     redirect are unchanged.
   - **Clients:** `skip_consent` is accepted on `POST`/`PUT
     /api/v1/clients` and returned on every read; `client.updated` records
     `skip_consent_before`/`_after`; `oauth_authorize.code_issued` records
     `consent_skipped`.
   - **Invite:** `POST /api/v1/users/:id/invite` also invites an
     unverified local user with no invite (it answered `409` for them).
   - **Audit log:** rows carry `organization_id` (the organization acted
     upon) and a filled `actor_type`; `actor_organization_id` is now the
     actor's own organization (it held whatever the call site set). An
     org_admin's `GET /api/v1/audit/events` returns its organization's rows
     whoever acted. Migration `0042` backfills `organization_id` only where
     an existing row's metadata names an existing organization; other rows
     from before stay visible to the organization they were filed under.
   - **Browser sign-in:** an organization that requires MFA enrols an
     unenrolled user on the sign-in form (the key and its `otpauth://`
     link, the recovery codes once, then a code).
   - **`identuum-idp bootstrap`** writes `setup.completed` and
     `user_created` (actor `system`) when it creates the site admin.

## Rolling back to v0.7.0

`v0.8.0`'s migrations are additive, and the `v0.7.0` binary does not know
them. Undo them, then run the `v0.7.0` image:

```bash
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U identuum_idp identuum_idp <<'SQL'
BEGIN;
-- 0042 down
DROP INDEX IF EXISTS idx_audit_events_organization_created_at;
ALTER TABLE audit_events DROP COLUMN IF EXISTS organization_id;
-- 0041 down
DELETE FROM mfa_pending_login_sessions WHERE kind = 'password_change';
ALTER TABLE mfa_pending_login_sessions DROP CONSTRAINT mfa_pending_login_sessions_kind_check;
ALTER TABLE mfa_pending_login_sessions ADD CONSTRAINT mfa_pending_login_sessions_kind_check CHECK (kind IN ('enroll', 'verify'));
DELETE FROM goose_db_version WHERE version_id IN (41, 42);
COMMIT;
SQL
cp docker-compose.v0.7.0.yml docker-compose.yml
docker compose up -d
```

Sessions carry over. A sign-in waiting at the password-change step (a
short-lived handle) starts again. Users created with a password under
`v0.8.0` stay verified and flagged `requires_password_change`, which
`v0.7.0` refuses at sign-in until an administrator clears it or the user
resets the password; first-party clients keep `skip_consent` (the `v0.7.0`
code honoured it but had no writer). Audit rows lose `organization_id`.
Restore the step-1 dump only if the database itself must go back; that
loses everything written after it.

## Known limitations

- **Separate sessions.** The console and the OpenID Connect sign-in keep
  separate sessions: signing in to one does not sign in to the other, and
  `end_session` does not sign the console out.
- **Older audit rows** carry `organization_id` only where their metadata
  named the organization; the others keep their earlier visibility. The
  OSS log is plain and retention-pruned (30 days by default); it has no
  hash chain.
- **A console sign-in that fails** for a known email is recorded as
  `anonymous` (no password was proven).
- **Single replica.** OSS enforces one serving instance (a DB lease); HA is
  a Professional+ capability.
