# identuum-idp-oss v0.9.10 — release notes

A security patch release. Tag `v0.9.10` on `main`. Published with the
manual `publish-image.yml` workflow (`version_tag: v0.9.10`, `latest_tag:
false`), dispatched on the tag; the index digest is recorded where the
compose file pins it. The Linux binaries are published with
`publish-binaries.yml` (`version_tag: v0.9.10`, `dry_run: false`), also
dispatched on the tag. The binary embeds identuum-ui `9e478fd`, which is
tagged identuum-ui `v0.9.10`.

## Security

**What you must do: upgrade.** Every install of `v0.9.9` or earlier should
move to `v0.9.10`.

**What your users will notice:** in an organization whose MFA policy is
`required`, a user who is signed in without a second factor keeps working
until their session next refreshes or their application next asks for a
token. They must then complete MFA. The upgrade signs nobody out.

The details are in `CHANGELOG.md` (`## v0.9.10`, Security). In short:

- A passkey assertion counts as user-verified only when the assertion itself
  says so.
- Sign-in through an upstream identity provider now applies the
  organization's MFA requirement, its local-sign-in-only setting and its
  session limit, and never links an upstream identity to an administrator
  account.
- A user cannot turn off their own second factor while their organization
  requires MFA.
- Completing a second factor re-checks the organization's session limit and
  its identity-provider-only setting.
- Session refresh, `/authorize` and the OAuth refresh grant require MFA when
  the organization requires it and the sign-in had none.
- Verifying a domain that another organization verified answers `409`
  instead of `500`, without naming that organization.
- Sign-in policy denials and session evictions are written to the audit log.
- New signing keys get a unique `kid` even when two are created in the same
  second.
- Go 1.27.2 and `golang.org/x/net` v0.60.0 fix GO-2026-6611, GO-2026-6612,
  GO-2026-6613 and GO-2026-6617 in `net/http` and HTTP/2.

## Other changes

- An organization created without a session limit takes
  `DEFAULT_MAX_SESSIONS_PER_USER` when it is a positive number, and 10
  otherwise.
- The API documentation says that an email verification link is single use.
- The console: the audit log's date range inputs follow the Time range
  select, and an administrator who has not activated reads as "activation
  pending".
- For Go callers that link identuum-idp-oss: new public packages
  `pkg/runtime`, `pkg/migrations` and `pkg/extension` (see
  `docs/PUBLIC-API.md`). A server whose database schema is at another
  version now stays up as NOT-SERVING with a fault that says to run
  `identuum-idp migrate`, instead of serving.

## Upgrading from v0.9.9

No migration runs: the schema stays at `0051`. No route was added, removed
or renamed; the endpoint count is 159. The database, the data volume, the
URL, browser sessions, issued tokens and the signing keys carry over.

1. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.9.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.9-backup.sql
   ```

2. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.10/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

3. **What can change for users and clients:** in an organization that
   requires MFA, users without a second factor are asked for one at their
   next refresh or token request, and applications holding a refresh token
   from such a sign-in get `invalid_grant` and must sign the user in again.
   Upstream sign-ins that the organization's rules do not allow are refused.

## Upgrading from v0.9.8 or earlier

Follow the `v0.9.9` notes first (and the earlier notes before them).

## Rolling back to v0.9.9

v0.9.10 adds no migration, so v0.9.9 starts on its database as it was.
Restore the compose file and recreate the containers:

```bash
cp docker-compose.v0.9.9.yml docker-compose.yml
docker compose up -d
```

A rollback brings back the weaknesses this release fixes.

## Known limitations

As in `v0.9.9`: a public client gets no refresh token; step-up and the other
second-factor proofs take only an authenticator code; an enrolment started in
Account settings lives in the running process for its five minutes; a token
minted for an API resource without an organization is active only to the
client it was issued to; resetting a user's password without email is an API
call; `IDENTUUM_IDP_TEST_ALLOW_PRIVATE_UPSTREAM_ISSUER` is for tests only;
requiring a verified email needs SMTP, a claim link needs
`IDENTUUM_IDP_UI_PUBLIC_BASE_URL`, the console and the OpenID Connect sign-in
keep separate sessions (D-023), and OSS runs one serving instance.

## Verification

`make verify-parallel`, the e2e mint, CI, the OpenID conformance run (both
plans against the committed floor), the upgrade from `v0.9.9` with data and
the rollback (a site_admin's and an org_admin's sign-in with their second
factor, a refresh token and the signing keys, both ways), the published
image digest, the binaries and a smoke test of the published compose file
are recorded with the publication.

SemVer: `0.9.10` is a patch release: it fixes security defects and adds no
migration; no route was added, removed or renamed. The new `pkg/` packages
add to the public Go API without changing any existing one.
