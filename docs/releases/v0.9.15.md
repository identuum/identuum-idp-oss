# identuum-idp-oss v0.9.15 — release notes

A verified passkey still counts after the password change an administrator
requested. An expired token no longer blocks a fresh sign-in, overlapping
setup completions have one winner, and setup-file handling is safer. The
build uses Go 1.27.3, which fixes GO-2026-6809 in crypto/x509.

This draft describes the changes in `v0.9.14..4a3157e`. Final console
binding, release checks and publication are still pending. Download
locations below are reserved for this version; no v0.9.15 artifact is
claimed published by this draft.

## What changes for you

- **If you sign in with a passkey and must choose a new password:** a
  passkey that verified you still satisfies MFA after the change. You are
  not asked for an authenticator code or MFA enrollment as well. Complete
  the change in the same browser that used the passkey.
- **If your client sends an old token while signing in:** an empty,
  expired or invalid Bearer value no longer blocks a fresh sign-in on the
  designated sign-in routes. You must still complete sign-in; the old
  value grants no access.
- **If you read setup instructions from container logs:** the startup
  banner no longer prints the setup code when stdout is not a terminal.
  Use the local `show-setup-code` command in the operator guide.
- **Before upgrading:** back up the database and its matching encryption
  key. This release adds migration 0057; rollback needs that backup.

## Changes

### Accounts and sign-in

- **Keep the verified passkey through the required password change.**
  When the server verified the passkey with user verification, the
  one-time password-change step carries that proof. After a valid new
  password, sign-in finishes at the phishing-resistant authentication
  level, whether or not an authenticator is enrolled. A presence-only
  passkey assertion follows the ordinary MFA policy after the change.
  The required password change and the expiry of an administrator-set
  password still apply.
- **Bind that proof to the client that made it.** The change needs both
  its one-time handle and the HttpOnly, SameSite=Strict cookie set by the
  passkey finish. A different client with only the handle is refused
  before the password changes. The embedded console forwards this cookie.
  Password sign-in and provider sign-in do not gain a passkey proof.
- **Allow fresh sign-in past an unusable Bearer value.** The exception
  applies to the designated sign-in method and path, with no principal
  taken from the old value. Authentication-store failures still refuse
  the request. Tests also cover a sample of other routes, methods and
  encoded spellings that must continue to refuse invalid values.
- **Find older mixed-case addresses in administrative lookups.** These
  lookups now trim and lowercase the submitted address and compare it
  against the stored address in lower case. Existing addresses are not
  rewritten. This extends administrative lookup; case-insensitive email
  sign-in already shipped in v0.9.14.

### Setup and operator tools

- **One winner for overlapping setup completions.** A completion with a
  valid setup code waits while another completion runs. If that other
  completion succeeds, the waiting request gets
  `410 setup_already_complete` without overwriting the winner. Tests also
  cover retry after a failure at the first active-signing-key read. This
  does not establish recovery from every failure point or add HA support.
  Embedded deployments that set their own database pool size need at
  least two connections; the default pool has 25.
- **Keep the setup code out of non-terminal startup output.** Pipes,
  files and the shipped no-TTY container configuration receive the command
  for displaying it locally instead. Terminal stdout still prints it.
  A terminal-attached container may retain that output through its
  configured logging; this is deployment guidance, not a log-retention
  proof. The change does not remove codes from older logs.
- **Protect setup-file reads and replacement.** File operations use an
  opened data directory and replace the setup file atomically, rather
  than truncating an existing entry. Reads reject symlinks and nonregular
  files, limit the file size and reject invalid contents. A symlink used
  for the data directory itself remains supported: operations stay on
  its opened target. World-writable data directories are refused.
- **Check before displaying the saved setup code.** `show-setup-code`
  refuses a file whose value does not match the hash in setup state.
  These are filesystem fixes found during gosec review; they are not a
  claim that every filesystem path or gosec finding is resolved.
- Recovery guides and Make targets keep operator passwords out of shell
  command text and explain recovery failures. Recovery auditing itself
  was introduced in v0.9.14.

### Organizations

- Organization deletion locks its service accounts in a consistent order
  to avoid the tested deadlock with communication-authorization creation.
  Service-account creation and organization deletion also share a
  lifecycle lock, so a create that waits for deletion finds the deleted
  organization and is refused.

### Build and tests

- The Go directive and the digest-pinned container builder move from
  Go 1.27.2 to Go 1.27.3. This addresses GO-2026-6809, the crypto/x509
  certificate-verification advisory disclosed for the v0.9.14 build.
- CI pins Grype 0.121.0 and its archive checksum. This scanner update is
  not a claim that the final images have already passed their scans.
- Integration fixtures keep their pools open until cleanup finishes and
  remove their own key rows. The rotation and issuer-confinement tests
  no longer leave those fixture keys behind. These are test fixes, not
  production signing-key changes or a whole-database cleanup guarantee.
- Tests cover the passkey proof, its client binding, setup concurrency,
  administrative email lookup and organization-deletion lock order.

### Console

The UI v0.9.15 changes update recovery documentation and add mocked tests
for public claim answers, request payloads and MFA continuation. They add
no console runtime behavior. Recovery auditing remains a server v0.9.14
feature. The final export revision and its equality with the embedded
console must be checked before publication.

## Upgrading from v0.9.14

This release adds `0057_pending_login_passkey_password_change.sql`.
The tracked `migrations/` directory contains 57 SQL files, head `0057`
(`git ls-files 'migrations/[0-9][0-9][0-9][0-9]*.sql' | wc -l`, measured
at `4a3157e`). The endpoint manifest still contains 166 entries
(`grep -c . tools/api-docgen/testdata/endpoints.manifest.txt`, measured
at the same revision); its contents are unchanged from v0.9.14.

0057 adds a pending sign-in kind and a client-binding column. The new
passkey kind requires a 32-byte binding; the earlier kinds require NULL.
Its Up section adds the column without a default and does not rewrite
rows. Schema review expects existing pending rows to receive NULL and
satisfy the new check. A populated-database upgrade proof on the final
candidate is still owed; this draft does not claim one has passed.

1. Follow [the operator guide](../OPERATOR-GUIDE.md) to back up the
   database, Compose file and matching encryption key.
2. Use the versioned Compose file and verify its checksum once published.
   The appliance runs migrations at start.
3. Check readiness and complete a fresh sign-in. A passkey user who owes
   a password change must finish it in the same browser.

No new setting is introduced. Use the embedded console for the new
cookie-bound step. If you skip v0.9.14, also follow its duplicate-email
pre-upgrade audit procedure before migration 0056 can apply.

For developers only: a disposable database that already applied an earlier
unreleased 0057 will not receive this tightened constraint by rerunning
migrations. Rebuild that development database through an authorized
procedure. This is not an instruction to rebuild a production database.

## Rolling back to v0.9.14

The v0.9.14 server refuses schema 0057. Stop the new server and restore the
verified pre-upgrade backup into an empty database before starting
v0.9.14, with the matching saved configuration and encryption key. Changes
since the backup are lost, including accounts, sessions and audit rows.
This is backup and restore, not a supported in-place migration-down
procedure. Sign in again after restoring; do not rely on a password-change
step begun on v0.9.15 surviving the restore. Rollback has not been proven
on the final candidate by this draft.

## Known limitations

- The cookie-bound passkey password-change step has not been validated
  with a console hosted on a separate origin. Use the embedded console.
- Code review finds that ordinary password-change completion does not
  recheck a switch to `idp_only`; the new check applies to the verified
  passkey completion. This is a review finding, not a live-test result.
- Code review also finds that changing the password and consuming the
  pending step are separate writes. A later failure can leave the new
  password set without a completed sign-in. No general atomicity fix is
  claimed here.
- CE customer-smoke licensed UI checks are not claimed passed. The UI
  text/tests-only exception must stay bound to the final release diff.
- Use HTTPS when opening the console from another device. Sign-in cookies
  require it outside localhost, 127.0.0.1 and host.docker.internal, and on
  every address when the issuer uses HTTPS.
