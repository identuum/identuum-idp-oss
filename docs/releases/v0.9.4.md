# identuum-idp-oss v0.9.4 — release notes

Tag `v0.9.4` on `main`. Published with the manual `publish-image.yml`
workflow (`version_tag: v0.9.4`, `latest_tag: false`), dispatched on the
tag; the index digest is recorded where the compose file pins it. The Linux
binaries are published with `publish-binaries.yml` (`version_tag: v0.9.4`,
`dry_run: false`), also dispatched on the tag. The binary embeds identuum-ui
`8121ba7`.

## Changes

This release fixes every finding of a security review of `v0.9.2` and the
code after it. Each fix has a test that failed first. The details are in
`CHANGELOG.md` (`## v0.9.4`); what matters to an operator:

- **Sign-in and tokens.**
  - A token issued to an app is no longer a credential for the IdP's own
    API. It still works at `userinfo`, at token introspection, and at the
    app's own resource servers.
  - A user signs in only to apps of their own organization. An app with no
    organization (registered by the site administrator) stays available to
    every organization.
  - `/authorize` and the consent page act only for a browser session.
  - A client introspects and revokes only its own tokens. A
    service-account token stops when its account or organization does.
  - A refresh-token family stops rotating 90 days after the sign-in that
    created it.
  - Sign-in through an upstream identity provider finishes only in the
    browser that started it (the login link and the callback must be on the
    same host).
- **Administrators.**
  - A site administrator no longer edits, resets, deletes or restores a
    tenant's users, nor decides their registrations. Appointing the first
    org admin of an organization that has none, and re-sending that invite,
    stays. The console's organization page shows the org admins as status
    only. A deleted tenant user cannot be restored over HTTP in this release.
  - An org admin cannot give an app a scope of the IdP's own catalogue that
    the admin does not hold.
- **"Skip consent"** (first-party apps) works only for confidential apps
  created in the console, signs in silently only for `openid`, `profile` and
  `email`, and is turned on with the admin's authenticator code. An existing
  first-party app that asks for more than identity now shows the consent
  screen for the rest.
- **Second factors.** Wrong codes are counted per user across all pending
  sign-ins and shared with step-up, MFA disable, recovery-code
  regeneration and turning skip consent on. A passkey proves the
  phishing-resistant level only when the authenticator verified the user.
  Adding or deleting a passkey needs a recent sign-in, and an admin's MFA
  reset removes the user's passkeys. New recovery codes carry 80 bits.
- **Brute force and enumeration.** Parallel wrong passwords stop at the
  failure threshold; the credential routes share a per-address limit of 120
  requests a minute; Argon2id runs in flight are capped; an unknown email
  costs what a known one does. Password reset, verification resend and
  self-registration no longer show by their response time whether an
  address has an account.
- **Sessions and sign-out.** The session cookie lasts as long as the
  browser unless "remember me" is ticked. A sign-out request with no
  `id_token_hint` shows a confirmation page. ID tokens carry `sid`, and
  back-channel logout reaches every app that holds an ID token for the
  session.
- **Pages and cookies.** The sign-in, consent and step-up pages carry a
  content security policy that loads nothing and runs no script (the
  passkey step-up page allows its one script by nonce). Cookies are `Secure`
  whenever the configured issuer is https.
- **Apps.** The grant types an app registers through dynamic registration
  are stored and enforced; an API-resource audience is unique across the
  installation; `client_credentials` for an API resource needs the resource
  in the client's `allowed_audiences`.
- **Image.** The runtime stage is distroless `static` (it was `base`),
  removing libc6 and libssl3 and their findings; the builder and prep
  digests are refreshed.
- **Operators.** The first request from a reverse proxy that is not in
  `IDENTUUM_IDP_TRUSTED_PROXIES` logs one `forwarded_header_ignored`
  warning.

## Upgrading from v0.9.3

Four migrations (`0044` to `0047`) run on start. No route was removed or
renamed, and the endpoint count stays 157. The database, the data volume,
the URL, browser sessions and issued tokens carry over.

1. **Check for a duplicated API-resource audience before upgrading.**
   Migration `0045` stops, and names the audiences, if two resources share
   one:

   ```sql
   SELECT audience FROM api_resources GROUP BY audience HAVING count(*) > 1;
   ```

   Rename or delete all but one of each, then upgrade. A resource server
   validates the audience it is given, so you decide which organization
   keeps it.

2. **Back up** the compose file and the database:

   ```bash
   cp docker-compose.yml docker-compose.v0.9.3.yml
   docker compose exec -T postgres pg_dump -U identuum_idp identuum_idp > identuum-idp-v0.9.3-backup.sql
   ```

3. **Replace the compose file and recreate the containers:**

   ```bash
   curl -fsSLO https://github.com/identuum/identuum-idp-oss/releases/download/v0.9.4/docker-compose.yml
   docker compose up -d
   ```

   Never run `docker compose down -v`: it deletes the install's database.

4. **What can change for clients:**
   - **First-party apps** that ask for more than `openid`, `profile` and
     `email` (an API audience, `offline_access`) now show the consent screen
     for the rest. An app registered through dynamic registration can no
     longer be first-party.
   - **`client_credentials`** for an API resource needs that resource in the
     client's `allowed_audiences`. Add it before upgrading, in the console.
   - **Dynamic registration:** an app that needs refresh tokens must register
     `refresh_token` among its `grant_types`. An app registered before this
     release, and an app created in the console, keeps every grant it had.
   - **Sign-out:** a request to `/api/v1/oidc/logout` without an
     `id_token_hint` shows a confirmation page when the browser holds a
     session.
   - **Recovery codes:** existing codes keep working. Regenerate them to get
     the longer ones.
   - **Tokens issued to an app** no longer open the IdP's own API. An app
     that used one that way must use its own credentials.

## Rolling back to v0.9.3

Four migrations were applied, and v0.9.3 has not been run against a v0.9.4
database. To go back, restore the compose file and the step-2 dump:

```bash
docker compose down
cp docker-compose.v0.9.3.yml docker-compose.yml
# restore identuum-idp-v0.9.3-backup.sql into the database, then:
docker compose up -d
```

That loses everything written after the dump.

## Known limitations

- **Requiring a verified email needs SMTP**; without it, the setting is
  refused (`400 smtp_not_configured`).
- **A claim link needs `IDENTUUM_IDP_UI_PUBLIC_BASE_URL`**; without it,
  nothing is issued (`409 claim_url_unavailable`).
- **Separate sessions** (D-023). The console and the OpenID Connect
  sign-in keep separate sessions.
- **Single replica.** OSS runs one serving instance (a DB lease); HA is a
  Professional+ capability.
- **The sign-in lockout counts failures per address.** Behind a reverse
  proxy that is not listed in `IDENTUUM_IDP_TRUSTED_PROXIES`, every user
  shares the proxy's address; the new warning names the proxy.
- **Back-channel logout** reaches the apps recorded after this release.
  A session whose tokens were issued earlier is notified through the app
  that asked, as before.
- **Mail after the response.** The reset, resend and registration mails are
  sent after the answer, so they arrive a moment after it.
